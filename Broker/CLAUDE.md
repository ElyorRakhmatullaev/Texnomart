# Client Broker

Operator-facing scoring application used in-store: after a client applies for BNPL/rassrochka, the operator picks a bank offer and walks the client through that bank's flow. Originated as a new sub-project bootstrapped in this monorepo (2026-08-17), starting with the **Alif Nasiya** flow; reworked end-to-end on 2026-08-18 per the designer's ТЗ for the missing Alif-integration screens; reworked again the same day (PM verbal clarification, second iteration) to move the whole Alif branch off its own routes and into a single popup hosted on «Выбор рассрочки». On 2026-08-19 the error/edge paths of that flow were filled in (PM checklist): reachable MyID photo/verification failures, OTP attempt limit + code expiry, a visible hold-cancelled state with cancel available from every later phase, and a permanent entry point back to the signed contract. **Reworked a third time on 2026-08-21** against a ТЗ written directly from Alif's API documentation (`alif_ui_tz.md`, 8 screens) — the popup grew from five phases to seven, gained a seven-status application model with an «Отменить заявку» action and Alif resale, moved instalment-term selection off the bank card into the popup's first screen, split "hold the prepayment" from "send the application to review" into two explicit steps, and turned card-attach into an Alif-owned screen of its own (additional data has been its own popup phase since the 18.08 rework already — this iteration reworked its *content*, from a fixed two-trustee form to a relatives list, not its ownership).

## Scope

Only the **Alif** bank branch is built. There are just **4 routes** (see below) — the entire Alif branch (offer/plan selection → card attach → additional data → application → hold → credit OTP → success) lives as **seven phases** of a single popup (`AlifCheckoutDialog`) hosted on `/scoring/banks`, not as its own routes. Login/PIN, real MyID/ML face verification, an in-app PDF previewer, other banks' branches, real API integration, polling an application's status, the Iman branch, «Подбор товара», and dark theme are out of scope — the mock enters directly at the «Верификация клиента» step with a seeded client and one pre-confirmed card. Clicking «Оформить» on a non-Alif bank shows a toast: «В прототипе реализован сценарий Alif».

## Flow (per screen)

1. **`/scoring/verification` — Верификация клиента.** Left: read-only seeded client fields (телефон / серия и номер паспорта / ПИНФЛ). Right: card list (seed: one card, already `confirmed`) + «Номер карты»/«Срок карты» inputs + green «Добавить». Adding a card validates, in order: duplicate mask → «Эта карта уже добавлена»; number ending `0000` → «Карта не найдена. Проверьте номер карты»; ending `9999` → AlertDialog «Карта заблокирована» («Лимит исчерпан на привязку. Карта заблокирована для привязки.»), no OTP shown; otherwise the card is added (unconfirmed) and `CardOtpDialog` opens. The OTP modal (`OtpPanel variant="card"`) asks for a 6-digit SMS code; `000000` fails with «Неверный код. Осталось попыток: N» and, after `OTP_MAX_ATTEMPTS = 3` failures, locks the input («Превышено число попыток. Запросите новый код»); the code also expires on its own after `OTP_TTL_SECONDS = 120` («Срок действия кода истёк. Запросите новый код»). Both locks are cleared only by «Отправить код повторно», which is therefore offered immediately in a locked state instead of waiting out the resend timer. Any other code confirms the card (toast «Карта подтверждена»). Clicking an unconfirmed card row reopens its OTP modal. «Продолжить» is enabled once ≥1 card is confirmed → `/scoring/myid`.

2. **`/scoring/myid` — Проверка MyID.** Camera capture via `getUserMedia` (hint chips «Держите положение лица» / «Не закрывайте лицо» / «Хорошее освещение», an oval face-positioning guide once the stream is live). Phases: `camera → preview → invalid|checking → rejected|done`. «Сделать снимок» captures a JPEG frame; «Переснять» / «Использовать фото» decide the preview. Two distinct failures, both cured by re-shooting: **`invalid`** — the photo is refused locally, before it is sent (red overlay + reason + «Переснять фото»); **`rejected`** — the photo was sent but MyID did not confirm the identity («Личность не подтверждена» + `MYID_REJECT_REASON` + a hint to retry or continue via support). Passing photo → `checking` phase (**~2,5 с** mock MyID check, `MYID_CHECK_DELAY_MS`) → `done` («Личность подтверждена») → «Продолжить» → `/scoring/banks`.

   **Demo-scenario switch.** Neither failure can arise on its own in the mock: `capture()` always yields a valid JPEG (canvas) and the mock MyID check always succeeds, so `validatePhoto` can no longer return an error and the failure screens were dead code. A small chip row under the hints («Демо-сценарий: Успех · Некорректное фото · Отказ MyID») lets the operator pick the outcome — the same deterministic-trigger idea as the card suffixes `0000`/`9999` and `OTP_FAIL_CODE`, just without an input field to hang it on. It is visible on every phase except `checking` and `done`, so the scenario can be switched before re-shooting; **it is a demo affordance and must be removed when a real MyID API is wired in.** If the camera is denied/unavailable, a «Камера недоступна» placeholder offers «Использовать демо-фото» (bundled `assets/demo-photo.jpg`, forced to `image/jpeg` MIME). «Вернуться к предыдущему шагу» → `/scoring/verification` (hidden during the `checking` phase only).

3. **`/scoring/banks` — Выбор рассрочки.** `ClientInfoBand` (seeded ФИО/телефон/ПИНФЛ/карта) + two `BankCard`s (Alif, Iman). Alif starts in a `pending` state («Рассчитывается…», skeleton rows) and flips to ready after **~6 с** (`ALIF_LIMIT_DELAY_MS`), mocking an async backend callback; Iman returns its limit instantly (`instantLimit: true`). «Оформить» on Alif just calls `openCheckout()` — condition/plan selection now lives *inside* the popup (экран 1), so there is nothing left to pick or freeze on the card itself. **The URL does not change**; the rest of the Alif branch (steps 3–5 of the stepper) plays out entirely inside `AlifCheckoutDialog`, a popup hosted right here on `/scoring/banks` (see below). «Оформить» on Iman just shows the out-of-scope toast. Once a заявка exists, `BankCard` also shows an `ApplicationStatusBadge` next to the offer badge; once `creditConfirmed`, the offer badge itself becomes green «✓ Оформлена» (instead of «✓ Одобрена») but the «Оформить» button stays enabled — clicking it again reopens the popup directly on its `success` phase (see «Reopen at success» below).

### Alif checkout popup (`AlifCheckoutDialog`, hosted on `/scoring/banks`)

A single Radix `Dialog` (`Broker/src/app/components/checkout/AlifCheckoutDialog.tsx`) is the phase-machine host for the whole Alif branch. It renders one of **seven** phase components (`checkout/*Phase.tsx`) — экраны 1–6 of the ТЗ, plus a `success` phase that covers экраны 7 (итог кредита) and 8 (договор) together, since the popup treats both as one screen. The header shows «Шаг N из 7 · <название фазы>» (`PHASE_STEP`/`CHECKOUT_STEP_COUNT` in `scoring-flow.tsx`) plus a thin `Progress` bar — a mini-stepper for the branch, separate from the 5-step `ScoringStepper` outside the popup (see «Stepper highlight» below).

**Terminal statuses are intercepted above the phase switch, not inside a phase.** `AlifCheckoutDialog` checks `state.sessionExpired`, then (`!state.creditConfirmed && application?.status === "REJECTED"`), then (`!state.creditConfirmed && application?.status === "CANCELLED"`) **before** rendering any `*Phase` component. `checkoutPhaseOf` does not look at `application.status` at all — it only asks whether an application *exists* — so a rejected or cancelled application would otherwise still derive to `hold` (экран 5 sits after `application` in the derivation) and a `REJECTED`/`CANCELLED` branch written *inside* `ApplicationPhase` or `HoldPhase` would never render. Both terminal screens offer «Назад к банкам» → `cancelOffer()`. The `!state.creditConfirmed` guard is defensive rather than currently live: the only path to `application.status === "CANCELLED"` is `cancelApplication()`, gated to `NEW`/`APPROVED` (`canCancelApplication`) — statuses that `confirmCredit()` overwrites with `ACTIVE` in the very same `setState` that flips `creditConfirmed`, so a cancelled application can no longer coexist with a confirmed credit through that path. `unsellApplication()` does **not** set `CANCELLED` — it returns the application to `ACTIVE` (see «Note — отмена продажи: расхождение с ТЗ» below). The guard earns its place anyway: it is exactly the safety net that would have kept a wrong status transition — an earlier version of `unsellApplication()` briefly did write `CANCELLED`, caught by QA on 2026-08-21 (`a179d0b`) — from silently replacing the finished contract screen with the «Заявка отменена» terminal.

**Phase derivation.** The active phase is **not stored** — it is derived on every render from `checkoutPhaseOf(state, alifPrepayment)` in `scoring-flow.tsx`. The checks read top-down as «what is blocking progress right now»:

| Order | Condition | Phase | Content | Stepper step |
|---|---|---|---|---|
| 1 | `state.creditConfirmed` | `success` | экраны 7+8 (`SuccessPhase`) — «Кредит оформлен! Договор №… подписан <дата>.» + «Заявка №235662235 в базе 1С Texnomart…» + «Скачать договор (PDF)» / «Посмотреть договор» / «Продать Alif» (`canSell`) / «Отменить продажу» (`canUnsell`) / green «Завершить скоринг» → `resetFlow()` + navigate `/scoring/verification` | 7 |
| 2 | `!state.offerConfirmed` | `offer` | экран 1 (`OfferPhase`) — plan list (3/6/12/18/24 мес., limit/ежемесячный платёж/комиссия/promo), «Рассчитываем лимиты…» loading, `Rejected` state (`ALIF_REJECT_REASONS`); «Продолжить» → `selectPlan(id)` + `confirmOffer()` | 1 |
| 3 | `!state.alifCard` | `card` | экран 2 (`CardAttachPhase`) — Alif's own `request-attach`, `OtpPanel variant="card"`, masked phone/PAN, `phone_match:false` warning, «Привязываем карту…» loading; success → `attachAlifCard()` | 2 |
| 4 | `!state.relations` | `details` | экран 3 (`DetailsPhase`) — relatives list + анкета; «Продолжить» → `saveDetails(relations, survey)` (one action saves both — no separate `survey` check exists in the derivation) | 3 |
| 5 | `!state.application` | `application` | экран 4 (`ApplicationPhase`) — товар из 1С + IMEI + дата первого платежа + итоги; «Создать заявку» → `createApplication()`, demo-selected outcome decides `NEW`/`REVIEWING`/`REJECTED`/one of 6 business errors | 3 |
| 6 | `alifPrepayment > 0 && (holdStatus !== "confirmed" \|\| application.status === "NEW")` | `hold` | экран 5 (`HoldPhase`) — prepayment hold, four statuses, «Отменить холд» gated by `canCancelHold` (`status === "NEW"`), explicit «Продолжить» → `submitForReview()` | 3 |
| — (fallback) | none of the above | `otp` | экран 6 (`CreditOtpPhase`) — `OtpPanel variant="credit"`, summary incl. ежемесячный платёж; success → `confirmCredit()` (stamps `contractNo`/`contractDate` via `makeContractNo()`/`new Date()`, keeps existing values, sets `application.status = "ACTIVE"`) | 4 |

**The hold condition is deliberately double, not a simple `holdStatus !== "confirmed"`.** After `holdConfirm()` the application stays `NEW` — a separate action, `submitForReview()` (the hold phase's «Продолжить» button), is what moves it to `REVIEWING`. Without the `|| application.status === "NEW"` clause, the derivation would leave the hold phase the instant the hold is confirmed, and `canCancelHold` (`status === "NEW"`) would become permanently unsatisfiable from any phase that can actually mount it — «Отменить холд» and the visible «Холд отменён» state would be dead code again, and `REVIEWING` would never be shown anywhere. This is exactly the class of defect the third iteration's reviews caught five times over (see `tasks/lessons.md`, 2026-08-21).

**Two positions in this table are load-bearing — do not reorder them:**
1. **`hold` (row 6) sits after `application` (row 5)**, per the ТЗ: an application is created `NEW` first, and only then is the prepayment held.
2. **`hold` sits above `otp`** — cancelling the hold must pull the operator *back* to the hold phase from any later phase, never leave them on a screen whose money is already unblocked. This is the exact bug fixed 19.08 (see `tasks/lessons.md`); reversing the order silently reintroduces it.

The seeded Alif `prepayment` (`ALIF_PREPAYMENT`) is `1_000_000` (non-zero), so `hold` is always on the path for the current seed; the `alifPrepayment > 0` clause exists for a future bank/seed where the hold phase is skippable end-to-end, and is not currently exercised.

**Cancelling the hold — only while `NEW`, and it lives on the hold phase, not on a status strip.** `HoldPhase` renders its own «Отменить холд» button (behind an AlertDialog: «… будут разблокированы на карте клиента … Введённые данные сохранятся»), visible only in the `confirmed` branch and gated by `canCancelHold(application.status)` — i.e. `status === "NEW"`. Confirming calls `holdCancel()` only — the phase change is a pure consequence of the derivation above, the component never navigates. This is the third iteration's rule (§2.3 of the spec), and it is a **deliberate rollback of the 19.08 PM checklist**, which had put «Отменить холд» on a `HoldStatusBar` strip shown on every later phase — see «Hold-cancel rule: 19.08 vs. 21.08» below for why, and for where the money-release capability moved.

`HoldStatusBar` still exists, but only as a **read-only** strip — «Предоплата удержана · сумма · карта» plus the note «Холд можно отменить, только пока заявка новая. Позже — через отмену заявки». It is mounted on exactly **one** phase: `otp` (`CreditOtpPhase`). It is *not* mounted on `details` or `application` — both come *before* `hold` in the derivation now, so a confirmed hold can never coexist with either of them; a copy of the strip was briefly present on both during implementation and was removed as dead code once the review caught it (see `tasks/lessons.md`, 2026-08-21). Rendering it defensively still checks `holdStatus === "confirmed"` and returns `null` otherwise, as a guard against state-derivation races rather than a normal code path.

**No more hold-exit lag.** The second iteration delayed leaving the `hold` phase by 600 ms (`HOLD_TO_DETAILS_DELAY_MS`) so the operator could see the green «Предоплата подтверждена» badge before the phase switched away. The third iteration removes that delay entirely — the constant is gone, and `AlifCheckoutDialog` reads `checkoutPhaseOf(...)` directly with no local phase mirror. The badge now stays visible for as long as the operator needs, because leaving the `hold` phase requires an explicit «Продолжить» click (`submitForReview()`), not an automatic transition — there is nothing left to race against.

**Close / resume semantics.** `checkoutOpen` persists in flow state (`sessionStorage`) alongside everything else, so closing the popup does **not** discard progress — `offerConfirmed`, `alifCard`, `relations`/`survey`, `application`, `hold`, `creditConfirmed` all survive, and the next «Оформить» / page reload reopens the popup on the same derived phase. Closing is possible via the × / Escape / overlay click **except** while `holdStatus === "held"` (the ~2 s auto-confirm window) — `handleOpenChange` plus `onPointerDownOutside`/`onEscapeKeyDown` all block it during that window. Leaving the branch entirely is a separate action, `cancelOffer()` («Вернуться к выбору предложения», reachable from `card`/`hold`) or «Назад» on `offer`, which resets `offerConfirmed`/`holdStatus`, clears `application`/`hold`, and closes the popup — a stale `NEW`/`REVIEWING` application left behind would otherwise dead-end a subsequent reopen on the «Заявка отменена» terminal (see «Terminal statuses» above). `planId` and `alifCard` deliberately survive `cancelOffer()`: экран 1 reopens with the plan pre-selected, and the operator does not have to re-enter the card code.

**Отменить заявку (`CancelApplicationDialog`).** A red text button in the popup header, visible whenever `state.application` exists and `canCancelApplication(application.status)` is true (`NEW` or `APPROVED`). Requires picking one of the nine `CANCEL_REASONS`; confirming calls `cancelApplication(reasonKey)`, which sets `application.status = "CANCELLED"` **and** releases the hold if it is `"held"` or `"confirmed"` (releasing it in the `"held"` branch matters — otherwise cancelling during the ~2 s auto-confirm window would leave `holdStatus` stuck and the popup permanently un-closable, since `HoldPhase` would have already unmounted under the `CANCELLED` terminal screen and its own `holdConfirm` timer would never fire). This is the **only** way out of the branch once the application has left `NEW` — see «Hold-cancel rule» below.

**Продать Alif / Отменить продажу.** Two buttons on the `success` phase (`SuccessPhase`), gated by `canSell`/`canUnsell` (`ACTIVE`→`SOLD`, `SOLD`→`ACTIVE`). Purely a status-model exercise — the signed contract and its download/view links stay on screen either way, since neither transition ever touches `creditConfirmed`. **This deliberately diverges from the ТЗ**, which specifies `SOLD`→`CANCELLED` — see «Note — отмена продажи: расхождение с ТЗ» below for why, and why it is still an open question.

**Reopen at success.** After `creditConfirmed`, the Alif `BankCard` badge switches to «✓ Оформлена» and its button is relabelled **«Открыть договор»** — it is neither hidden nor disabled, so a click just calls `openCheckout()` again, and since `checkoutPhaseOf` sees `creditConfirmed` first, the popup reopens straight on the `success` phase, never restarting the flow.

**Hold-cancel rule: 19.08 vs. 21.08 — a deliberate conflict, resolved in the ТЗ's favour.** The 19.08 PM checklist made «Отменить холд» reachable from every later phase (a `HoldStatusBar` strip on `details`/`otp` of the *then*-5-phase popup) — that was correct **for that popup shape**, where hold sat before additional data and the application didn't exist yet as a concept. The 21.08 ТЗ (экран 5, §4) states plainly that cancelling the hold is allowed **only while the application is `NEW`** — after the hold, the application moves on to review, and by the API's own model a held prepayment tied to a reviewing/approved application is no longer a "just changed my mind" cancellation, it is an application-level decision. The spec resolved the conflict by following the ТЗ, on the grounds that it is written against the real backend and describes actual API-enforced behaviour, while the PM checklist was a UI-only decision made before the application concept existed. **The ability to release the held money did not disappear — it moved.** Once the application leaves `NEW`, releasing the prepayment happens through «Отменить заявку» (`CancelApplicationDialog`, gated `NEW`/`APPROVED`), which cancels the application *and* releases the hold in one action. There is no gap: `REVIEWING` in the mock lasts only ~2.5 s (`APPLICATION_REVIEW_DELAY_MS`) before auto-advancing to `APPROVED`, where «Отменить заявку» is available again. Two separate cancel buttons on one screen was deliberately avoided — `HoldStatusBar` lost its action entirely rather than duplicating «Отменить заявку»'s effect.

**Stepper highlight (`ScoringStepper.tsx`).** For the 3 real routes, the active step index comes from the pathname (`activeIndexFor`, steps 0/1/2). While `state.checkoutOpen` is true **and the current route is `/scoring/banks`** (the only route that hosts the popup — a browser-Back to `/scoring/myid` with `checkoutOpen` still true falls back to pathname mapping), the index instead comes from `PHASE_INDEX[checkoutPhaseOf(state, ALIF_PREPAYMENT)]` — `offer`/`card` → step 3 (index 2, same as «Выбор рассрочки»), `details`/`application`/`hold` → step 4 (index 3), `otp`/`success` → step 5 (index 4). So opening the popup visually advances the outer stepper through steps 3→4→5 without the URL ever leaving `/scoring/banks` — steps 4–5 have no route/page of their own, they are reachable only as popup-phase highlights. The finer «Шаг N из 7» progress inside the popup header (`PHASE_STEP`) is a separate, more granular indicator layered on top of this.

The floating `ActionRail` (right edge, ≥lg only) is available on every screen, but not interactive while the popup is open — the modal overlay (`z-50`) sits above it (`z-10`) and disables pointer events on the rest of the page; reset while the popup is open happens via the popup's own controls, or by closing the popup first. Otherwise: «Завершить скоринг» opens an AlertDialog confirmation and, on confirm, does the same `resetFlow()` + navigate-to-verification as the success phase's green button.

## State — `ScoringFlowProvider`

`Broker/src/app/scoring-flow.tsx` — React context backed by **`sessionStorage`** under the key **`broker:scoring-flow:v2`** (bumped from `broker:scoring-flow` — see «Deleted from the 21.08 API-ТЗ rework» above). The flow survives a page reload but resets on a new session (tab/browser close). `resetFlow()` clears the key and returns to `INITIAL` (cards reseed to the one pre-confirmed `SEED_CARD`).

Actions: `markAlifLimitReady()`, `selectPlan(planId)`, `setAlifLimitStatus(status)`, `attachAlifCard(card)`, `addCard(mask, expiry)`, `confirmCard(mask)`, `removeCard(mask)`, `setPhotoDone()`, `setMyidDone()`, `holdHold()`, `holdConfirm()`, `holdCancel()`, `confirmOffer()`, `cancelOffer()`, `openCheckout()`, `closeCheckout()`, `saveDetails(relations, survey)`, `createApplication(application)`, `setApplicationStatus(status)`, `submitForReview()`, `cancelApplication(reasonKey)`, `sellApplication()`, `unsellApplication()`, `expireSession()`, `refreshSession()`, `confirmCredit()`, `resetFlow()`.

`holdCancel()` vs `cancelOffer()` vs `cancelApplication()` are three deliberately separate actions at three different scopes: `holdCancel()` only flips `holdStatus` to `"cancelled"` (operator stays on the hold phase, everything else untouched); `cancelOffer()` abandons the branch entirely (resets `offerConfirmed`/`holdStatus`, clears `application`/`hold`, closes the popup — `planId`/`alifCard` survive); `cancelApplication(reasonKey)` cancels the application in place (sets `application.status = "CANCELLED"` + `cancelReasonKey`, releases the hold if `"held"`/`"confirmed"`, does **not** close the popup or touch `offerConfirmed` — the operator lands on the `CANCELLED` terminal screen inside the same branch).

See the phase table under «Alif checkout popup» above for the exact per-phase conditions and their check order.

## Mock Conventions

All magic values live in `src/lib/broker-mock-data.ts`.

- **OTP failure code**: `000000` (`OTP_FAIL_CODE`) — used identically by all three OTP hosts (card confirmation on step 1, Alif's own card attach on экран 2, credit confirmation on экран 6, hosted by the shared `OtpPanel`); any other 6-digit code succeeds. **OTP resend timer**: `OTP_RESEND_SECONDS = 60`. **Attempt limit**: `OTP_MAX_ATTEMPTS = 3` — each miss counts down («Осталось попыток: N»), the third locks the field. **Code lifetime**: `OTP_TTL_SECONDS = 120` — a live countdown («Код действует M:SS») that, on reaching zero, locks the field with «Срок действия кода истёк». Both locks disable the input and the CTA, and both are cleared only by «Отправить код повторно» — which is offered immediately (bypassing the 60 s resend timer) whenever the panel is locked, since waiting it out would be pointless. `OTP_TTL_SECONDS > OTP_RESEND_SECONDS` on purpose: a new code can always be requested before the old one dies.

## Application status model, business errors, cancel reasons — `lib/alif-application.ts`

A pure, React-free module (no imports from the rest of the app) — the single source of truth for the application's non-UI logic, read by both the popup phases and `BankCard`.

- **`ApplicationStatus`** (7 values) + **`APPLICATION_STATUS_META`** — label + Tailwind classes per status, per §5 of the ТЗ: `NEW` серый · `REVIEWING` жёлтый(amber) · `APPROVED`/`ACTIVE` зелёный(emerald) · `REJECTED` красный · `SOLD` синий(blue) · `CANCELLED` серый. Rendered by `ApplicationStatusBadge`, used in the popup header and on `BankCard`.
- **Action-availability predicates** — `canCancelApplication(status)` (`NEW`/`APPROVED`), `canCancelHold(status)` (`NEW` only), `canSell(status)` (`ACTIVE`), `canUnsell(status)` (`SOLD`). Kept here rather than inlined in components because the same rule is read from more than one place (the popup header, `HoldPhase`, `SuccessPhase`).
- **`APPLICATION_ERRORS`** — six named business-error keys (`duplicate_marking`, `has_reviewing`, `has_new`, `amount_too_small`, `scoring_reject`, `amount_too_large`), each with the ТЗ's exact Russian message and, for two of them, which form field to highlight (`marking`/`amount`). Surfaced on экран 4 by `PhaseError` + `ApplicationPhase`'s field ring.
- **`CANCEL_REASONS`** — the ТЗ's nine `cancel_reason_key` options verbatim, consumed by `CancelApplicationDialog`.
- **`buildPlans(limits, principal)`** — turns `ALIF_LIMITS` seeds into `AlifPlan[]` (adds `monthlyPayment`/`commission`); called independently (with the same seed + the same `ORDER.amount - ALIF_PREPAYMENT` principal) from `OfferPhase`, `ApplicationPhase`, `CreditOtpPhase`, and `SuccessPhase` — all four therefore always agree on the numbers, since they derive from one function rather than each computing its own.

## Note — отмена продажи: расхождение с ТЗ

⚠️ `alif_ui_tz.md` (§5, таблица статусов) описывает «Отменить продажу» как переход `SOLD` → `CANCELLED` — тот же статус, что и настоящая отмена заявки (`cancelApplication()`). Мок сознательно ставит его в `SOLD` → `ACTIVE` (`unsellApplication()` в `scoring-flow.tsx`). Причина: при `CANCELLED` статусная таблица самого ТЗ показала бы бейдж «Отменено» рядом с текстом «Кредит оформлен» на том же экране успеха, а `canSell(status)` (гейт на `ACTIVE`) больше никогда не пропустил бы кнопку «Продать Alif» обратно — оформленный кредит нельзя было бы продать повторно. Решение принято на финальном QA-ревью 21.08 (коммит `a179d0b`) и отражено здесь, в коде (`scoring-flow.tsx`) и в спеке (`docs/superpowers/specs/2026-08-21-broker-alif-api-tz-design.md`, §5). **Это единственный открытый вопрос, оставленный текущей итерацией** — расхождение нужно подтвердить с бэкендом Alif: либо ТЗ переиспользует `CANCELLED` там, где по смыслу нужен другой статус, либо API действительно ожидает именно `CANCELLED`, и тогда экран успеха и правила `canSell`/`canUnsell` придётся переосмыслить вместе, а не менять один мок в одностороннем порядке.

## Demo affordances (delete at real API integration)

All demo-only inputs for this branch — the ones with nothing real behind them to trigger a given outcome — are collected in **one file, `checkout/DemoScenarioBar.tsx`**, rendered as a thin strip at the bottom of the popup by `AlifCheckoutDialog` itself, below whichever phase is active. This mirrors the same problem the 19.08 lesson already named for MyID (an error branch nothing can reach is dead code) — the third iteration adds several more unreachable outcomes at once (scoring rejection on экран 1, `phone_match: false` on экран 2, three statuses + six business errors on экран 4, session expiry everywhere), so this time they were built as one panel instead of scattered per-phase chips:

- **`offer` phase**: «Одобрено» / «Отказ скоринга» toggles `alifLimitStatus` (`"ready"`/`"rejected"`) directly.
- **`card` phase**: «Телефон совпадает» / «Телефон не совпадает» toggles `phoneMatch`. This value is **not** phase-local state — it is owned by `AlifCheckoutDialog` (which hosts both the bar and `CardAttachPhase`) and passed down as a prop to both, because `sessionStorage` alone doesn't give same-tab components a live update when one of them writes it (no `storage` event fires in the writing tab). An earlier version kept a separate copy in each component and they silently disagreed — see `tasks/lessons.md` (2026-08-21).
- **`application` phase**: a `Select` with eight outcomes — «Заявка принята» (→ `NEW`/`REVIEWING` depending on prepayment) · «Отказано» (→ `REJECTED`) · one option per business error (`APPLICATION_ERRORS`). There is **no** «Одобрено сразу» option — `APPROVED` is only ever reached by the review-delay timer advancing a `REVIEWING` application, so a demo path straight to `APPROVED` would name a status the app never actually assigns that way (would also silently break `canCancelHold`/`submitForReview`, which assume every application starts `NEW`).
- **Always available, any phase**: «Сессия истекла» — sets `sessionExpired`, which `AlifCheckoutDialog` intercepts before the phase switch (see «Terminal statuses» above); «Обновить сессию» clears it and returns to the same phase.

Read/write helpers for the two persisted demo settings (`readDemoPhoneMatch`/`writeDemoPhoneMatch`, `readDemoApplicationOutcome`/`writeDemoApplicationOutcome`) live in the same file, keyed under `broker:demo-phone-match` / `broker:demo-application-outcome` in `sessionStorage` — deliberately **not** part of `ScoringFlowState`, since these are test-rig settings, not оформление data. **This entire file, plus its one host call in `AlifCheckoutDialog`, is meant to be deleted in one move when a real Alif API is wired in** — same intent as the pre-existing MyID demo chips (`MYID_DEMO_SCENARIOS`, still in `MyIdPhotoPage.tsx`, untouched by this iteration and not unified with this panel).

## When Adding New Pages

1. For a new gated *route*: add it (+ any `RequireStage` guard, extending the `Stage` union in `routes.tsx`) in `src/app/routes.tsx`. For a new *phase* of the Alif checkout popup: add a case to `checkoutPhaseOf()` in `scoring-flow.tsx` (respect the top-down most-advanced-wins check order — see the two load-bearing orderings called out under «Alif checkout popup» above), a `checkout/<Name>Phase.tsx` component, and a branch in `AlifCheckoutDialog.tsx` + `PHASE_STEP`/`PHASE_INDEX` in `scoring-flow.tsx`/`ScoringStepper.tsx` — do not add a route for it. Verify by grep, not just a green build: `vite build` here transpiles via esbuild and does not type-check, so a phase left out of a `Record<CheckoutPhase, ...>` or a stale reference to a deleted symbol compiles silently (see `tasks/lessons.md`, 2026-08-19/21).
2. Create the component under `src/app/components/<feature>/`
3. Follow Patterns A–K (see root CLAUDE.md) — this app does not use the shared `AppShell`; extend `BrokerShell`/`ScoringStepper` instead (the outer stepper is a flat 5-step constant — do not reintroduce branching)
4. Extend `ScoringFlowState` in `scoring-flow.tsx` for any new persisted flow data
5. Use mock data from `src/lib/broker-mock-data.ts` or extend it
6. All text in Russian
7. Use `@texnomart/ui/` for primitives (Button, Card, InputOTP, Dialog, etc.) — open modals with a plain `<button>`/`Button` trigger, not `asChild` Radix triggers (a known off-screen-menu gotcha elsewhere in this monorepo)
8. Mobile responsive — test at sm/md/lg breakpoints
