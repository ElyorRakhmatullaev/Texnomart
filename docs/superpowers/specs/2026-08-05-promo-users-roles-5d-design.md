## 1. Задача

Комментарии БА по разделу «Управление пользователями» помечены «Частично сделано»: раздел существует, но роли ведутся плоским списком, временных прав с периодом нет, статус «Деактивирован» не выражен, происхождение учётки не фиксируется, а журнал действий не показывает, что именно изменилось.

Блок закрывает 24 уникальных подпункта (строки 66 и 67 несут идентичный текст follow-up БА — дубль).

### 1.1. Gap-анализ (проведён построчно против кода 2026-08-05)

## 2. Архитектурное решение

### 2.1. Реестр ролей вместо плоского списка

`users-store.ts`, аддитивно:

```ts
export type RoleKind = "primary" | "additional" | "temporary";

export interface RoleAssignment {
  role: PromoRole;
  kind: RoleKind;
  /** Только для kind==="temporary". ISO date-only «YYYY-MM-DD», окно включительно. */
  from?: string;
  to?: string;
  /** ФИО назначившего — консистентно с `KdSubstitution.assignedBy`. */
  assignedBy?: string;
  assignedAt?: string;
  /** Основание/комментарий. */
  reason?: string;
}

interface PromoUser {
  // ...существующие поля без изменений
  roleAssignments?: RoleAssignment[];
  /** ФИО создателя учётной записи (G1). */
  createdBy?: string;
}
```

Ровно одна `primary`-запись; `additional` и `temporary` — сколько угодно.

### 2.2. Новый чистый модуль `Promo/src/lib/user-roles.ts`

Единственная деривация состояния ролей — тот же приём, что `audit-access.ts` (5C), `plan-approval.ts` (Волна 4), `full-calendar-status.ts` (Волна 2). Модуль **не импортирует стор** (иначе цикл: стор → user-roles → стор), а принимает минимальный носитель:

```ts
export interface RoleCarrier {
  role: PromoRole;
  roles?: PromoRole[];
  roleAssignments?: RoleAssignment[];
}

/** Реестр ролей. Если `roleAssignments` нет — строится из `roles[]`/`role`:
 *  roles[0] → primary, остальные → additional. Обратная совместимость по конструкции. */
export function assignmentsOf(user: RoleCarrier): RoleAssignment[];

/** Активна ли временная запись на момент ref (окно [from,to] включительно, локальная полночь). */
export function isAssignmentActive(a: RoleAssignment, ref?: Date): boolean;
export function isAssignmentExpired(a: RoleAssignment, ref?: Date): boolean;

/** Постоянные роли (primary + additional) — база для гвардов. */
export function permanentRolesOf(user: RoleCarrier): PromoRole[];

/** Постоянные + временные, действующие на ref. Читается ВЕЗДЕ, где нужны «текущие права». */
export function activeRolesOf(user: RoleCarrier, ref?: Date): PromoRole[];

export function primaryRoleOf(user: RoleCarrier): PromoRole;
export function temporaryAssignments(user: RoleCarrier, ref?: Date): RoleAssignment[];
```

Дата-арифметика — по образцу `kd-substitution-store.localMidnight` (локальная полночь, без UTC-сдвига).

`rolesOf` в `users-store` становится однострочной обёрткой над `activeRolesOf`, поэтому все существующие потребители (`UsersPage`, `UsersTable`, `UsersFilters`, `UserFormDialog`, `UserDetailPage`, `NotificationItem`, `kd-substitution-store`, `users-xlsx`) получают корректный набор без правок вызовов.

**Автоснятие временной роли = вычисление при чтении.** Планировщика в моке нет и он не нужен: `activeRolesOf` не вернёт роль, чьё окно прошло. Это и есть требование «после окончания периода временная роль должна сниматься автоматически».

### 2.3. Гварды администраторов считают постоянные роли

`usableAdminCount` / `canRevokeAdmin` / `canDeactivate` переводятся на `permanentRolesOf`. Временный «Администратор» не держит пул ≥2 — иначе в день истечения окна система осталась бы без администраторов, а гвард отчитался бы, что всё в порядке.

Это применение урока 5C «вводя общую модель вместо частных гейтов, проверьте, что новая не ШИРЕ прежней»: при переходе на реестр каждый гейт проверяется отдельно на вопрос «постоянные или активные роли здесь правильны».

Отдельно: `canRevokeAdmin` симулирует отзыв, подменяя роли пользователя на `["Сотрудник закупа"]`. Симуляция переводится на реестр — снимается только постоянная запись «Администратор», временные записи в симуляции сохраняются, иначе гвард посчитает не то состояние, которое реально наступит.

### 2.4. Замещение КД — проекция, а не слияние

`kd-substitution-store` остаётся единственным источником замещения, и **гейтинг не меняется**: `canActAsKd`, конфликт интересов, баннеры S3 и `auditScopeFor` работают как сейчас. Ноль правок в S3.

Проекция — только для отображения: `substitutionBadgeFor(user, ref)` возвращает `{ label: "Уполномоченное лицо КД", from, to } | null` и рисуется чипом рядом с ролями в списке и в профиле (G11).

**Почему замещение НЕ кладётся в `activeRolesOf`:** роли «Уполномоченное лицо КД» нет в `PROMO_ROLES`, а спроецировать её на «Коммерческий директор» значит расширить права — заместитель немедленно получил бы всё, что гейтится по этой роли (`permissions.ts`, матрица прав, фильтры, навигация), тогда как трекер (стр. 70) прямо ограничивает замещение этапом согласования КД и запрещает выдавать админ-права.

Дополнительно в панели замещения:
- «История замещений» → `Collapsible`, по умолчанию **свёрнута**, в заголовке счётчик записей (G5);
- третье состояние записи — **«Срок истёк»** (окно прошло, отзыва не было) рядом с «активно» и «снято досрочно» (G6);
- причина замещения попадает в аудит как основание (G7).

### 2.5. Аудит: структурные изменения вместо строки-комментария

```ts
export interface AuditFieldChange { field: string; before: string; after: string; }

interface AuditEvent {
  // ...существующие поля
  changes?: AuditFieldChange[];   // G9
  reason?: string;                // основание/комментарий действия (G10)
}
```

Оба поля опциональны, поэтому все существующие сиды и живые события валидны без правок.

Типы действий: `«блокировка»` → **`«деактивация»`**, `«разблокировка»` → **`«восстановление»`** (формулировка клиента, стр. 71). Переименование затрагивает `AuditActionType`, `AUDIT_ACTION_META`, `NON_KEY_ACTIONS` (5C), сиды и два места вызова (`UsersPage`, `UserDetailPage`). Новых типов действий не добавляем: перечень клиента полностью покрывается существующими («создание», «изменение профиля», «изменение ролей», «сброс пароля», «назначение/снятие замещения»).

Требование «пароль не отображается в журнале» удерживается тем, что `changes[]` для парольных действий не заполняется вовсе — фиксируется только факт.

Отображение: колонка «Изменения» в `/audit` → «Аудит-лог»; строки «Поле: было → стало» и «Основание» в журнале `/users/:id`; колонка в выгрузке `audit-xlsx`.

## 4. Сиды

- `createdBy` проставляется всем восьми сид-учёткам («Администратор Системы» для существующих).
- Одна **активная** временная роль (окно покрывает демо-дату) и одна **истёкшая** — иначе состояния «действует до DD.MM» и «срок истёк» нечем показать в браузере.
- Активное сид-замещение (`sub-1`, u-8, до 31.12.2026) остаётся; для ветки «Срок истёк» в историю добавляется одна прошедшая запись.

## 5. Что НЕ входит в блок (YAGNI)

- Не вводим 10-ю роль в `PROMO_ROLES`.
- Не трогаем S3, `canActAsKd`, конфликт интересов и баннеры замещения.
- Не добавляем планировщик/таймер: истечение считается при чтении.
- Не трогаем god-mode переключатель ролей — он остаётся отдельным демо-механизмом поверх реальных ролей пользователя (ограничение мока, зафиксировано ещё в E-4).
- Не переносим замещение КД в реестр ролей (см. 2.4).

## 6. Риски и как они снимаются

| Риск | Снятие |
|---|---|
| `rolesOf` начинает исключать истёкшие роли — потенциальная регрессия доступа | У существующих сидов временных ролей нет ⇒ поведение идентично; новые сиды добавляются осознанно. После правки — сверка «было/стало» по каждой из 9 ролей. |
| Гварды администраторов посчитают временную роль | Явно переведены на `permanentRolesOf` (2.3). |
| Переименование типов действий ломает 5C-фильтры | `NON_KEY_ACTIONS`, `AUDIT_ACTION_META` и сиды правятся в одной задаче с переименованием; вкладка «Все действия» проверяется кликом. |
| Транспайл-онли сборка не видит расширения юниона | После каждой задачи — открытие экрана в браузере; при расширении `AuditActionType` грепается имя типа, чтобы найти все `Record`/`switch`. |
| Проекция замещения расширит права | Замещение не попадает в `activeRolesOf` — только в отображаемый чип (2.4). |
| Сохранение формы редактирования потеряет временные роли | `UserFormDialog` работает с `RoleAssignment[]`, а не с плоским `PromoRole[]`: `UserFormValue.roles: PromoRole[]` → `assignments: RoleAssignment[]`, и `UserDetailPage.handleEditSubmit` сравнивает/пишет реестр. Иначе `setUserRoles(value.roles)` на сохранении молча превратил бы временные роли в постоянные (или удалил их) — тот же класс дефекта, что «правка согласованной строки уходила не туда» в Волне 2. |
