# Promo — Авторизация и учётные записи (под-проект #0 + A)

> Спек-документ. Дата: 2026-06-29. Проект: **Texnomart Promo**.
> Источник требований: «Комментарии по авторизации, правам доступа и интерфейсу промо-календаря» (2-я часть), раздел **1. Авторизация и управление учётными записями**.

## Контекст

Это первый из четырёх под-проектов, на которые декомпозирован третий раунд клиентской обратной связи по промо-календарю:

| # | Под-проект | Статус |
|---|---|---|
| **#0 + A** | **Авторизация и учётки** (этот спек) | проектируется |
| B | Тёмная тема (рефактор захардкоженных цветов → токены) | отложен |
| C | Профиль и Настройки (экраны) | отложен |
| D | Матрица прав (документ + консолидация) | отложен |

Под-проекты A, C, D опираются на общий фундамент #0 («текущий пользователь» + стор пользователей), поэтому #0 проектируется и строится вместе со своим первым потребителем — управлением учётками (A). B полностью независим. C переиспользует смену пароля из A. D пересекается с A по аудит-логу.

### Текущее состояние (что уже есть)

- Поток входа: `/login` → `/login/2fa` → `/` с демо-усложнениями: 30%-случайный успех, 6-значная 2FA, блокировка после 5 неудач (`Promo/src/app/components/auth/LoginPage.tsx`, `Login2FAPage.tsx`, общий `packages/shared/src/auth/auth-context.tsx`).
- Один захардкоженный пользователь «Сардор Мавлянов» в `Promo/src/app/shell-config.tsx`.
- 9 ролей + свободный демо-переключатель (god-mode) в шапке, активная роль в `sessionStorage` (`Promo/src/app/role-context.tsx`).
- Аудит-лог `/audit` (S8) есть, но реконструирован из сидов и «протухший» — не пишет действия в сессии.
- Нет управления пользователями, временных паролей, обязательной смены пароля.

## Цели и критерии успеха

1. После входа по логину/паролю пользователь **сразу** попадает в систему (без 2FA).
2. В системе есть **не менее двух** активных пользователей с ролью Администратор (основной + резервный).
3. Администратор может: создавать пользователей, сбрасывать пароли, назначать и отзывать права администратора.
4. При создании учётной записи пользователю выдаётся **уникальный временный пароль**; при первом входе система **требует его обязательную смену**.
5. Действия администраторов (создание, сброс пароля, назначение/отзыв прав) **фиксируются в аудит-логе** с указанием пользователя и роли.

## Границы (scope)

**Входит:**
- Реальный «текущий пользователь» + стор пользователей (localStorage).
- Вход без 2FA, с проверкой пароля по стору.
- Временный пароль + **принудительная** смена при первом входе.
- Экран «Управление пользователями» (создание, сброс пароля, назначение/отзыв админа, деактивация).
- Живая дозапись действий администратора в аудит-лог.

**Не входит (другие под-проекты):**
- Тёмная тема (B).
- Экраны Профиль/Настройки (C). Здесь делается только **принудительный** экран смены пароля; **добровольная** смена из Профиля — это C.
- Общая матрица прав по ролям (D).

## Архитектура и решения

### Уровень хранения
**localStorage** — только для модуля учёток и аудита. Остальной прототип остаётся in-memory как есть. Обоснование: создание пользователя, вход под временным паролем и фиксация в аудите теряют смысл, если исчезают при перезагрузке.

### Модель личности и ролей
- Логин аутентифицирует конкретного пользователя из стора → он становится «текущим пользователем» (заменяет захардкоженного «Сардора» в `shell-config.tsx`).
- Активная роль по умолчанию = роль вошедшего пользователя.
- **Свободный демо-переключатель 9 ролей в шапке остаётся** — клиент в п.4 фидбэка явно хочет поведение «переключил роль → интерфейс поменялся».
- Гейтинг UI остаётся на **активной роли** (через `useRole()`), консистентно со всем приложением.
- «Администратор» — это одна из 9 существующих ролей (одна роль на пользователя). «Назначить/отозвать права администратора» = сменить роль пользователя на/с «Администратор».

### Модель данных

Новые модули:

`Promo/src/lib/users-store.ts`
```ts
type UserStatus = 'active' | 'temp-password' | 'blocked'

interface PromoUser {
  id: string
  fullName: string        // ФИО
  email: string           // = логин
  role: PromoRole         // одна из 9 ролей
  status: UserStatus
  password: string        // mock: простая строка, НЕ настоящий хэш
  mustChangePassword: boolean
  createdAt: string       // ISO
}
```
- Сиды (≥2 админа): основной Администратор `admin@texnomart.uz`, резервный Администратор, «Сардор Мавлянов» (Коммерческий директор) и ещё несколько пользователей под разные роли.
- API стора: `getUsers`, `getUserByEmail`, `createUser` (генерит уникальный временный пароль, `status: 'temp-password'`, `mustChangePassword: true`), `resetPassword` (новый временный пароль + флаг), `setRole` (назначить/отозвать админа), `setStatus` (деактивация/активация), плюс guard-функция `usableAdminCount` = число пользователей с ролью «Администратор» и `status !== 'blocked'` (то есть `active` **или** `temp-password` — заблокированные не считаются, т.к. не могут войти). Чтение/запись через localStorage с сидами как стартовым состоянием.

`Promo/src/lib/audit-store.ts`
- Живые события дозаписываются в localStorage (`AuditEvent`, переиспользуя тип из S8 `promo-mock-data.ts`).
- Экран `/audit` сливает сиды (`AUDIT_EVENTS_SEED`) + живые события из стора, новые сверху.

### Поток входа и сессия
1. Удаляем роут `/login/2fa` из `Promo/src/app/routes.tsx`. Общий `auth-context` не трогаем (Dashboard не затронут).
2. Вход: email + пароль сверяются со стором (`getUserByEmail` + сравнение пароля).
   - Неверные данные → внятная ошибка + счётчик неудач.
   - После 5 неудач — блокировка на 15 мин (логика уже есть, переиспользуется, привязывается к реальной проверке).
   - 30%-случайный успех убирается.
3. Успех:
   - `status === 'blocked'` → отказ во входе с сообщением.
   - `status === 'temp-password'` (или `mustChangePassword`) → жёсткий редирект на **принудительный экран смены пароля**; в систему не пускает, пока новый пароль не задан. Переиспользуется `ResetPasswordPage` со счётчиком надёжности (10+ символов, заглавные/строчные/цифра/спецсимвол). После смены: `status: 'active'`, `mustChangePassword: false`.
   - иначе → вход в систему; «текущий пользователь» установлен; активная роль = роль пользователя.
4. Логин-форма **предзаполнена основным админом** `admin@texnomart.uz`, чтобы управление учётками было видно сразу при демонстрации этого модуля.

### Экран «Управление пользователями»
- Новый роут `/users`. Пункт меню виден **только при активной роли Администратор** (так же, как `/promo-types` гейтится под КД/Администратор) — добавляется в `shell-config.tsx` с `roles: ["Администратор"]`.
- **Список** (Pattern C: таблица в Card со sticky-заголовком → карточки Pattern K ниже md): ФИО · email · роль (badge) · статус (badge) · дата создания · меню действий.
- **Действия:**
  - «Создать пользователя» — диалог (ФИО / email / роль) → система генерит уникальный временный пароль → показывает админу **один раз** в диалоге результата с кнопкой «Скопировать». Пользователь сохраняется со `status: 'temp-password'`.
  - «Сбросить пароль» — генерит новый временный пароль (показывается один раз), `status: 'temp-password'`, `mustChangePassword: true`.
  - «Назначить администратора» / «Отозвать права администратора» — меняет роль на/с «Администратор».
  - «Деактивировать» / «Активировать» — переключает `status` между `active` и `blocked`. **Без жёсткого удаления** (паттерн «no hard delete», как в типах промо).
- **Защита ≥2 админов:** отзыв прав администратора или деактивация запрещены, если `usableAdminCount` (Администраторы со `status !== 'blocked'`) после операции станет меньше двух (кнопки задизейблены + поясняющий тултип).
- Каждое из перечисленных действий → запись в аудит-лог: пользователь (текущий) + активная роль + время + объект (пользователь) + тип действия + комментарий.

## Mock-ограничения (зафиксировать в реализации)

- localStorage привязан к конкретному браузеру — не общий бэкенд; «сброс демо» = очистка хранилища.
- «Пароли» хранятся как простые строки, не настоящий хэш — это прототип.
- «Передача временного пароля» = показ админу на экране (почты/SMS-бэкенда нет).
- God-mode переключатель ролей: гейтинг управления учётками — по активной роли, поэтому формально любой вошедший может переключиться в Администратора. Это принятое демо-поведение; помечается как mock-ограничение.
- Аудит становится живым **только для действий этого модуля**; остальные экраны (S3/S4/…) по-прежнему seed-stale.

## Решения, принятые по делегированию (могут быть пересмотрены)

1. Админ = роль «Администратор» (одна роль на пользователя), а не отдельный флаг поверх роли.
2. Гейтинг управления учётками — по активной роли (переключатель), консистентно с приложением.
3. Деактивация вместо удаления (no hard delete).
4. Логин предзаполнен основным админом `admin@texnomart.uz` (а не «Сардором»-КД).
