## 1. Задача

### 1.1. Бизнес-контекст (из MD)

Заявка уходит во все банки сразу; каждый возвращает лимит. После выбора банка процесс становится банк-специфичным. У **Alif** — самый длинный хвост: **4 экрана** после выбора банка (у Open Bank — 0), **два РАЗНЫХ OTP-кода** в разное время (привязка карты, затем подтверждение кредита), дополнительная форма о родственниках и договор PDF. Особенность скоринга: иногда в ответе приходит только `client_id`, а лимит — позже через callback → фронту нужен **индикатор ожидания** и polling.

Ключевые UX-требования PM:
- **Два отдельных шага с OTP** — визуально разные этапы, не один общий экран.
- **Ожидание лимита** после выбора Alif на экране 2 — лоадер/индикатор.
- Все 4 экрана — **только для ветки Alif**.

### 1.2. Gap-анализ против Figma «Client Broker»

Канвас уже содержит операторское приложение: топ-бар (логотип + адрес магазина · «Подбор товара» / «Скоринг» · RU/UZ · пользователь), жёлтый 5-шаговый степпер (Верификация клиента → Проверка MyID → Выбор рассрочки → Дополнительные данные → Информация по рассрочке), плашка клиента (ФИО / телефон / ПИНФЛ / карта), карточки банков (Alif Nasiya, Iman Invest, OPEN Birinchi, Anor/Axiom Nasiya) с чипами сроков, лимитом и жёлтой «Оформить», правая рейка действий (Новая вкладка · Отправить лимиты в Telegram · Завершить скоринг), скелетоны загрузки, секция «Messages» с ошибками.

| Экран сценария Alif | В Figma | Вывод |
|---|---|---|
| Экран 2 «Результаты банков» | Есть — «3-step: Choose BNPL» (9 фреймов, вкл. состояние ожидания «Ваш запрос отправлен, сейчас проходит оценка, ожидается ответ» + кнопка-лоадер «Загрузка» + скелетон) | Реализовать по Figma, в сокращённом объёме |
| Экран 3 «Привязка карты» (OTP №1) | **Нет** | **Спроектировать новый** |
| Экран 4 «Доп. данные» | Есть — «4-step: Additional Info» (доверительные лица + дата списания) | Реализовать по Figma внутри ветки Alif |
| Экран 5 «Подтверждение кредита» (OTP №2) | **Нет** | **Спроектировать новый** |
| Экран 6 «Успех» | Частично — «5-step: BNPL Info» (зелёная панель «Скоринг произведен, заявка №… в базе 1С создана» + «Завершить скоринг»), но **без номера договора и «Скачать договор (PDF)»** | **Спроектировать Alif-вариант** |
| Степпер ветки Alif | Нет (степпер всегда 5 шагов) | **Спроектировать расширение** |

### 1.3. Рассмотренные подходы

- **A. Минимальная ветка Alif (выбран).** Bootstrap `Broker/`; вход сразу на «Выбор рассрочки» с посеянным клиентом; карточки банков + состояние ожидания лимита Alif; 4 экрана ветки Alif; расширенный степпер; деплой третьим приложением на Pages. Ровно закрывает таск-лист.
- **B. Полный поток с логина.** + Login/PIN, верификация, MyID (~20 доп. экранов). Отклонён: 3–4× скоупа вне таск-листа (YAGNI); добавляется следующими итерациями.
- **C. Только отрисовка в Figma (code-to-design).** Отклонён как основной трек: плейсхолдер `Broker/` и паттерн репозитория указывают на код; отрисовка возможна как follow-up с готовых экранов.

### 2.2. Оболочка — собственный топ-бар, не AppShell

Осознанное отступление от чек-листа: Figma-макет — операторский терминал с **верхней** навигацией, сайдбар-AppShell сюда не подходит. Собственный `BrokerShell` (только в `Broker/src/`):

- Хедер 64px, белый: слева жёлтый квадрат-логотип (астериск) + «Ташкент, Янги Шахар, 16а»; по центру «Подбор товара» (неактивный пункт-заглушка, toast) и «Скоринг» (активный, полужирный); справа RU | UZ (display-only) и аватар «Мирхомитов Миржалол».
- Без авторизации: приложение загружается сразу в скоринг (логин — вне скоупа).
- Правая плавающая рейка (desktop ≥ lg): круглые кнопки «Новая вкладка», «Отправить лимиты в Telegram», «Завершить скоринг» (первые две — toast; «Завершить скоринг» — AlertDialog подтверждения → сброс потока → `/scoring/banks`).

### 2.3. Маршруты (React Router v7, `basename` по BASE_URL)

| Маршрут | Экран |
|---|---|
| `/` | redirect → `/scoring/banks` |
| `/scoring/banks` | Экран 2 «Выбор рассрочки» |
| `/scoring/alif/card` | Экран 3 «Привязка карты» (OTP №1) |
| `/scoring/alif/details` | Экран 4 «Дополнительные данные» |
| `/scoring/alif/confirm` | Экран 5 «Подтверждение кредита» (OTP №2) |
| `/scoring/alif/success` | Экран 6 «Успех» |

Гварды: `/scoring/alif/*` требуют состояния потока (выбран Alif с лимитом) — иначе redirect на `/scoring/banks`; `success` требует пройденного подтверждения. Кнопки «Вернуться к предыдущему шагу» и браузерный back работают согласованно (обычная навигация назад по маршрутам).

### 2.4. Состояние — `ScoringFlowProvider`

React-контекст + `sessionStorage` (`broker:scoring-flow`) — поток переживает перезагрузку страницы, но не «новую сессию» (соответствует смыслу скоринговой сессии):

```ts
interface ScoringFlowState {
  client: BrokerClient;                    // посеян: ФИО, телефон, ПИНФЛ, карта 4860 **** **** 1251
  order: { amount: number; tenor: number };
  alif: {
    limitStatus: "pending" | "ready";      // pending → ready через мок-callback (таймер ~6 с)
    limit?: number;
    cardAttached: boolean;                  // экран 3 пройден
    additionalData?: AdditionalData;        // экран 4
    creditConfirmed: boolean;               // экран 5 пройден
    contractNo?: string;                    // генерится на подтверждении, формат ALF-2026-XXXXXX
    oneCOrderNo?: string;                   // «заявка в 1С», генерится вместе с договором
  };
}
```

Мок-данные — `Broker/src/lib/broker-mock-data.ts`: клиент, банки (id, название, логотип-цвет, лимит, сроки, предоплата, статус), тексты, константы таймеров. Никаких изменений в shared-пакетах.

## 3. Дизайн экранов

Общий каркас каждого экрана: хедер → степпер → серый фон `bg-gray-50` → плашка клиента → контентная карточка по центру (макс. ширина ~560–880px) → правая рейка. Токены — общие для монорепо (#FFD60A, Inter, радиус 10px, тень карточек).

### 3.0. Степпер ветки Alif

На «Выборе рассрочки» — исходные 5 шагов (1–2 отмечены пройденными, 3 активен). После «Оформить» у Alif степпер **расширяется до 7 шагов**: Верификация клиента ✓ → Проверка MyID ✓ → Выбор рассрочки ✓ → **Привязка карты** → **Доп. данные** → **Подтверждение кредита** → Информация по рассрочке. Это главный носитель требования «два OTP — два разных этапа»: оба шага видны в степпере одновременно, у каждого своя позиция и подпись. На <md степпер сворачивается в компактную строку «Шаг N из 7 · <название>» + тонкий прогресс-бар.

### 3.1. Экран 2 — «Выбор рассрочки» (реализация по Figma, сокращённая)

- Плашка клиента: ФИО · Номер телефона · ПИНФЛ · Карта (4 колонки, как в Figma).
- Сетка карточек банков (2 колонки ≥ lg, 1 — mobile): **Alif Nasiya**, **Iman Invest**. Карточка: логотип + название + бейдж статуса («Одобрена» зелёный soft-tint), чипы сроков (2/3/6/9/12/18/24/36 мес. у Alif; выбранный — белая «таблетка»), панель «Доступный лимит / Срок / Предоплата» в жёлтой рамке, жёлтая кнопка «Оформить».
- **Состояние ожидания Alif (ключевое требование):** при входе карточка Alif в состоянии `pending` — бейдж «Рассчитывается…» (янтарный soft-tint), вместо панели лимита скелетон + строка «Ваш запрос отправлен, сейчас проходит оценка, ожидается ответ» со спиннером, кнопка задизейблена «Загрузка». Через ~6 с (мок callback + polling из MD) карточка анимированно переходит в `ready`: бейдж «Одобрена», лимит 8 546 000 сум, «Оформить» активна. Iman Invest готов сразу — контраст поведения виден.
- «Оформить» (Alif) → переход в ветку: `/scoring/alif/card`. «Оформить» (Iman) → toast «В прототипе реализован сценарий Alif».
- Под сеткой — свёрнутая плашка «Запрос лимита у партнеров ▾» (display-only, как в Figma).

### 3.2. Экран 3 — «Привязка карты» (OTP №1) — новый

Центральная карточка (~560px):

- Чип этапа: **«Код 1 из 2 · Привязка карты»** — нейтральный серый soft-tint + иконка `CreditCard`.
- H2 «Привязка карты», подзаголовок: «Мы отправили SMS с кодом на номер, привязанный к карте **4860 •••• •••• 1251**».
- `InputOTP` на 6 ячеек (44px, крупные цифры, автофокус).
- Строка повторной отправки: «Отправить код повторно через 0:59» (обратный отсчёт 60 с → активная ссылка «Отправить код повторно» → toast + перезапуск таймера).
- Primary жёлтая **«Подтвердить»** (активна при 6 цифрах), под ней текстовая «Вернуться к предыдущему шагу» (→ `/scoring/banks`).
- Валидация мока: любой полный код проходит, кроме `000000` — демонстрация ошибки: красная обводка ячеек + «Неверный код. Проверьте SMS и попробуйте ещё раз» + очистка.
- Успех → `cardAttached = true`, toast «Карта привязана», переход `/scoring/alif/details`.

### 3.3. Экран 4 — «Дополнительные данные» (по Figma)

- Caption «Log Id: 123456», H2 «Дополнительные данные», подзаголовок «Укажите контакты близких — это увеличивает шанс одобрения».
- Две колонки (≥ md): «Доверительное лицо — 1» (обязательное): Номер телефона (+998-маска) + «Вид родства» (select: Брат / Сестра / Отец / Мать / Супруг(а) / Коллега / Другое); «Доверительное лицо — 2» — те же поля, необязательное.
- Блок «Дата списания оплаты»: поле даты (по умолчанию сегодняшнее число следующего месяца).
- Жёлтая «Продолжить» (валидация: телефон №1 полный + вид родства выбран), «Вернуться к предыдущему шагу».
- Состав полей — допущение №3 (в MD «уточнить у бекенда»); отмечено в `Broker/CLAUDE.md`.

### 3.4. Экран 5 — «Подтверждение кредита» (OTP №2) — новый, визуально отличён

Тот же каркас `OtpStepCard`, но с намеренными отличиями (требование «не путать пользователя»):

- Чип этапа: **«Код 2 из 2 · Подтверждение кредита»** — зелёный soft-tint + иконка `FileSignature` (вместо серого + `CreditCard`).
- Сводка кредита над полем ввода (компактная панель): Банк «Alif Nasiya» · Сумма 10 000 000 сум · Срок 6 мес. · Лимит 8 546 000 сум — на экране 3 такой панели нет.
- H2 «Подтверждение кредита», подзаголовок: «Мы отправили **новый код** для подтверждения оформления кредита».
- Callout (амбер, иконка `Info`): «Это другой код — не тот, что вы вводили при привязке карты. Введите код из последнего SMS.»
- Primary жёлтая **«Завершить»** (не «Подтвердить»), та же логика resend/ошибки (`000000` → ошибка).
- Успех → `creditConfirmed = true`, генерация `contractNo` (ALF-2026-XXXXXX) и `oneCOrderNo`, переход `/scoring/alif/success`.

Носители различия шагов: позиция в степпере, номер в чипе («1 из 2» / «2 из 2»), цвет чипа, иконка, панель сводки, текст callout, подпись CTA. 

### 3.5. Экран 6 — «Успех» — Alif-вариант финала

Двухпанельная раскладка финального шага из Figma:

- Слева — карточка выбранной рассрочки: логотип Alif Nasiya + бейдж «Оформлена» (зелёный), чип срока «6 мес.», панель «Доступный лимит / Срок / Предоплата», строка «Договор № **ALF-2026-XXXXXX**» + дата оформления.
- Справа — зелёная панель успеха: круглая иконка-галочка, заголовок «Кредит оформлен!», текст «Договор №ALF-2026-XXXXXX подписан. Заявка №235662235 в базе 1С Texnomart создана автоматически — продолжайте оформление продажи в ней.» Кнопки: **«Скачать договор (PDF)»** (outline, иконка `Download` — отдаёт мок-PDF `public/contract-mock.pdf` с именем `Договор_ALF-2026-XXXXXX.pdf`) и зелёная **«Завершить скоринг»** (сброс потока → `/scoring/banks`).

### 3.6. Состояния и краевые случаи

- **Перезагрузка** на любом шаге ветки — состояние из sessionStorage, экран восстанавливается; прямой заход на шаг без пройденных предыдущих — redirect по гвардам (2.3).
- **Back** из экрана 4 на экран 3: карта уже привязана — экран 3 показывает состояние «Карта привязана ✓» с задизейбленным вводом и кнопкой «Продолжить» (повторный OTP не запрашиваем).
- Ошибки сети/сервера — вне скоупа (Messages-экраны Figma); ошибки мока ограничены неверным OTP.
- Скелетоны — только Pattern I (карточка Alif в ожидании); спиннеров-страниц нет.
