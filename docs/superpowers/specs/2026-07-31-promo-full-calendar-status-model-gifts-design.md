# Полный промо-календарь — построчная модель статусов + отображение подарков

> **Раунд:** «10-я часть» client feedback (29.07.2026), «Волна 2».
> **Источник:** `10я_часть_комментарий_Общее_по_дизайну_29_07_2026` (Ч1 + Ч2), раздел
> «1. Полный промо-календарь», Блоки 1–7; трекер R46 + R44 (+ 6-я PDF «Продолжение»,
> раздел «Полный промо-календарь. Отображение подарков»).
> **Область:** только `Promo/`, только экран `/full-calendar`. Shared/Dashboard не трогаем.
> **Дата:** 2026-07-31.

## Проблема

Сейчас состояние строки полного календаря собрано из разрозненных сигналов:
`campaign.status`, `line.rejected` (S3), `line.removalPending`/`line.removed` (S4 §5.3),
диф правок-после-согласования `changedCells` (янтарная обводка ячейки), `pending1CCheck`,
плюс бейдж в band «N изм. после согл.» и пять плашек рядом с наименованием (дубль /
ожидает 1С / отклонена / ожидает исключения / исключена).

Клиент (Блоки 1–7) хочет **одну построчную модель статуса**, выраженную через:
- **единый фильтр «Все статусы»** (11 значений, Блок 7);
- **визуальное состояние строки** (Блок 1): светло-оранжевая подсветка **только** для
  повторных действий, ожидающих согласования; «Черновик» — компактная пометка;
  отменённые — серый + зачёркивание;
- **боковую панель «Детали изменений»**, открываемую **иконкой-глазом** «просмотр
  деталей» в строке (Блоки 4.3/5.3/6.7);
- **красный индикатор** для КМ по отклонениям (Блок 6);
- отказ от отдельных статусных/версионных плашек рядом с номенклатурой (Блок 1.2).

Референс-скрин (Ч2, стр. 3) прямо показывает целевой вид и подтверждает эту модель;
клиент помечает его как «визуальный ориентир, не точное требование к дизайну».

## Не входит в объём (следующие волны)

- **Блок 4.4 (хвост):** «новая позиция не попадает в финальные отчёты как согласованная» —
  это логика **отчётов** → Волна 5.
- **«Дополнение. Карточка согласования» (Ч2, стр. 5–6, R57):** переработка карточки
  повторного согласования (`/approvals/:id`) → **Волна 3** (строится на модели этой волны).
- **«Распределение по категориям» (Ч2, стр. 7, R74):** действие КД «Распределить по
  КМ/категориям» на этапе согласования плана → **Волна 6**.
- **Отчёты §6 (выравнивание чисел, Ч2, стр. 4, R52.C/R60):** → Волна 5.

## Терминология

- **Позиция / строка = `PromoLine`.** Клиентские «состояния позиции» — это построчные статусы.
- **«Последние согласованные данные» = baseline** = строки последней отправленной версии
  (`getCampaignVersions` / `PROMO_LINES` для базовой версии). Уже вычисляются для дифа
  правок-после-согласования.
- **«Повторное действие» (repeat action)** = изменение согласованной позиции, добавление
  позиции после согласования промо, запрос на исключение. Только эти подсвечиваются
  светло-оранжевым (Блок 1.3).

## Часть A — Отображение подарков (R44, малый объём, низкий риск)

Клиент (6-я PDF «Продолжение» + трекер R44.C): в блоке подарков непонятно, какая механика
используется, потому что всё падает в блок «Подарок №1».

1. **Переименование колонок:** группа колонок «Подарок №1»/«Подарок №2» →
   **«Подарок (1)» / «Подарок (2)»** (`gridFields.ts`, поля `gift1*`/`gift2*` labels).
   Для фиксированных типов («Товар в подарок», «1+1») это два отдельных блока-подарка
   в одной строке промо — как и сейчас.
2. **Механика «Подарок на выбор»:** для кампании типа `giftChoice` колонка «Подарок (1)»
   получает **подпись-заголовок «Подарок на выбор»** над списком вариантов (внутри ячейки,
   первой строкой блока), «Подарок (2)» = «—». Варианты уже рендерятся списком по одному в
   под-строке, основная номенклатура объединена по вертикали (Блок из 6-й PDF: «основная
   номенклатура не дублируется, объединённая ячейка») — оставляем, только добавляем подпись.
3. **Индикатор механики в band:** маленький чип у номера промо — «Подарки: на выбор» либо
   «Подарки: 2 фиксированных» (по `isGiftChoiceType` / `isGiftType`), чтобы механика была
   очевидна без раскрытия ячейки.
4. **«+ Добавить подарок»** уже работает (проверено в QA Волны 1) — сохраняем, проверяем в QA.

Часть A самодостаточна и не зависит от Части B; собираем её первой (быстрый видимый прогресс).

## Часть B — Построчная модель статусов (R46, Блоки 1–7)

### B1. Новая чистая деривация `lineDisplayStatus`

Новый модуль **`Promo/src/lib/full-calendar-status.ts`** (чистые функции, без React):

```ts
export type LineStatus =
  | "Черновик"
  | "На согласовании (общее)"            // синтетика фильтра, не хранится в строке
  | "На согласовании у старшего КМ"
  | "На согласовании у коммерческого директора"
  | "Переотправлено на корректировку КМ"
  | "Изменения на согласовании"
  | "Исключение на согласовании"
  | "Отклонённые изменения"
  | "Согласовано"
  | "Согласовано и отправлено смежным отделам"
  | "Отменена / Удалена";

export function lineDisplayStatus(campaign: PromoCampaign, line: PromoLine): LineStatus
```

**Приоритет деривации** (сверху вниз, первый матч побеждает):

1. `line.removed` → **«Отменена / Удалена»** (Блок 5.4/5.5).
2. `line.removalPending` → **«Исключение на согласовании»** (Блок 5.1).
3. `line.pending?.rejected` (повторное действие отклонено) → **«Отклонённые изменения»** (Блок 6.6).
4. `line.pending?.action === "addition"` → **«Изменения на согласовании»** (Блок 4.4 — новая
   позиция после согласования = повторное действие; отдельного значения фильтра для
   «добавления» в Блоке 7.2 нет, поэтому маппим в «Изменения на согласовании»).
5. `line.pending?.action === "change"` → **«Изменения на согласовании»** (Блок 4.1).
6. `campaign.cancelled` → **«Отменена / Удалена»** (вся акция отменена).
7. Иначе — по `campaign.status`:
   - `"Черновик"` (или fresh-editable внеплановая до первой отправки) → **«Черновик»** (Блок 3.1).
   - `"Переотправлено на корректировку КМ"` **или** `line.rejected` (первичное отклонение)
     → **«Переотправлено на корректировку КМ»** (Блок 6.5).
   - `"На согласовании у старшего КМ"` → **тот же** (Блок 3.3).
   - `"На согласовании у коммерческого директора"` → **тот же** (Блок 3.3).
   - `"Согласовано и отправлено смежным отделам"` → **тот же** (Блок 7.4 — держим отдельно).
   - fallback → **«Согласовано»** (согласовано, но ещё не отправлено смежным — редкий случай
     в моке; напр. согласованная правка до инкрементальной отправки).

**Синтетика фильтра `"На согласовании (общее)"`** (Блок 3.4/7.3) — не возвращается из
`lineDisplayStatus`, а сопоставляется предикатом в фильтре:

```ts
export const PENDING_APPROVAL_STATUSES: LineStatus[] = [
  "На согласовании у старшего КМ",
  "На согласовании у коммерческого директора",
  "Изменения на согласовании",
  "Исключение на согласовании",
];
export function matchesStatusFilter(status: LineStatus, filter: string): boolean
// filter === "Все статусы" → true;
// filter === "На согласовании (общее)" → PENDING_APPROVAL_STATUSES.includes(status);
// иначе → status === filter.
```

Все 11 значений мока достижимы через сиды (см. B6).

### B2. Модель «последние согласованные данные» + `line.pending` (Блок 2 — ключевое решение)

Клиент (Блок 2.1–2.2, 4.2): в основной таблице по согласованным позициям с
несогласованными правками показываем **последние согласованные значения**; новые значения —
**только в боковой панели** до согласования. Сейчас мы делаем наоборот (показываем правку +
янтарная обводка).

**Решение:** правки согласованной позиции не мутируют отображаемые поля строки, а
записываются в **`line.pending`**:

```ts
export interface LinePendingChange {
  action: "change" | "addition";           // exclusion остаётся на removalPending/removed
  /** для action==="change": пофайловый диф от baseline. */
  fields?: { field: keyof PromoLine; label: string; was: string; now: string }[];
  by: string;                               // роль-отправитель (в моке нет пер-персон identity)
  at: string;                               // ISO дата отправки на повторное согл.
  comment?: string;
  requestType: string;                      // «Тип запроса», напр. «Изменение цен и прогноза», «Добавлена номенклатура»
  /** заполняется при отклонении повторного действия → «Отклонённые изменения» + красный индикатор. */
  rejected?: { by: string; at: string; reason: string };
  /** снимается, когда КМ открыл детали (красный индикатор, Блок 6.4). */
}
```

- Поле добавляется в `PromoLine` как **опциональное** (`pending?: LinePendingChange`) —
  обратная совместимость: строки без него ведут себя как раньше.
- **Отображение в таблице:** `CellValue` рендерит согласованные (текущие) значения строки
  как обычно; `line.pending` **не** меняет ячейки. Никакой янтарной обводки ячеек (уходит).
- **Подсветка строки:** светло-оранжевая, если есть активное повторное действие
  (`line.pending && !line.pending.rejected`) **или** `line.removalPending` (Блок 1.3/4.1/5.1).
  Первичное согласование и согласованные строки — без подсветки (Блок 1.4).
- **Правки-после-согласования (live):** обработчик `edit` для **согласованной** кампании
  (`isApprovedCampaign`) диффит патч против отображаемого значения и пишет `line.pending`
  вместо мутации полей. Правки **черновика** (fresh) по-прежнему мутируют поля напрямую
  (первичное заполнение, подсветки нет).
- **Согласование повторных изменений (Блок 2.3):** при согласовании (это делает КД в S3/S4,
  здесь — демо-переход) значения `pending.fields.now` вливаются в строку, `line.pending`
  очищается, подсветка снимается. В моке достаточно кнопки-перехода в панели/семечка + сид.
- Существующие `diffCampaignChanges` / `changedCells` / band-бейдж «N изм. после согл.» —
  **убираем** из грида (заменяются `line.pending` + подсветкой строки; Блок 1.2/13). Функции
  в mock-data оставляем (могут использоваться отчётами) — но грид их больше не рендерит.

**Взаимодействие с S4 Phase 2 (правки-после-согласования).** Текущая презентация S4 Phase 2
— янтарная обводка изменённой ячейки + band-бейдж «N изм. после согл.» + чип «Ожидает
маркетинга» — **вытесняется** моделью `line.pending` (подсветка строки + панель). Хелперы
маршрутизации в mock-data (`diffCampaignChanges`, «Ожидает повторного согласования
маркетинга») **остаются** для отчётов/будущего, но грид перестаёт их показывать. Сам
workflow повторного согласования правок (кто и как их утверждает) — это карточка
согласования (Волна 3 / R57), в объём 10-й части по полному календарю не входит.

*Отклонённая альтернатива:* показывать отредактированные значения (текущее поведение) — прямо
противоречит Блоку 2, поэтому не рассматриваем.

### B3. Боковая панель `LineDetailsDrawer` (новый компонент)

Новый **`Promo/src/app/components/full-calendar/LineDetailsDrawer.tsx`** (Sheet справа),
открывается **иконкой-глазом** в строке (у каждой строки повторного действия / отклонения /
исключения; для остальных строк иконка тоже есть, но панель показывает базовые детали).
Секции по референсу (Ч2, стр. 3) + Блоки 4.3/5.3/6.7:

- **Заголовок:** статус строки (напр. «Изменение на согласовании») + № промо + номенклатура.
- **Информация об акции:** Номенклатура · Тип промо · Название акции · Период акции.
- **Изменение** (для `action==="change"`): таблица **Поле · Было · Стало** (из `pending.fields`).
  Для `action==="addition"` — «Добавлена номенклатура» + данные строки.
  Для `removalPending`/`removed` — тип «Запрос на исключение из промо» + причина.
- **Детали запроса:** Тип запроса · Кто отправил · Дата отправки · Комментарий.
- **История согласования / отклонения:** «Отправлено на согласование» + текущий статус;
  при `pending.rejected` — «Отклонено: кто · дата · причина» (Блок 6.7).

Панель **только для просмотра** в этой волне (действия «Согласовать/Отклонить строку» из
панели — это карточка согласования, Волна 3 / R57). Открытие панели по строке с отклонением
снимает красный индикатор для КМ (B5).

### B4. Единый фильтр «Все статусы» (Блок 7)

- В `FullCalendarPage` фильтр `key: "status"` (сейчас по `CAMPAIGN_STATUSES`, применяется к
  кампании) → **«Все статусы»** по `LineStatus`, применяется **построчно** к
  `lineDisplayStatus(campaign, line)`.
- Значения фильтра = 11 `LineStatus` + «Все статусы» (дефолт) + «На согласовании (общее)».
- Никаких отдельных пер-статусных фильтров (Блок 7.1). Остальные фильтры (Тип, КМ, Признак,
  № промо, Период) — без изменений.
- Фильтрация построчная: кампания показывается, если хотя бы одна её видимая строка проходит
  фильтр; band кампании остаётся, непрошедшие строки скрываются (консистентно с текущей
  построчной фильтрацией КМ `displayLinesFor`).

### B5. Красный индикатор для КМ (Блок 6)

- Новый **`Promo/src/lib/full-calendar-rejection-store.ts`** (localStorage, per-user, паттерн
  E-серии): множество «просмотренных отклонений» ключом `lineId`.
- Индикатор (красная точка у иконки-глаза) показывается **только для роли КМ**, только когда
  по строке принято отрицательное решение (`line.rejected` — первичное, **или**
  `line.pending.rejected` — повторное) **и** `lineId` ещё не в множестве просмотренных
  (Блок 6.1/6.2). Для строк, которые только ожидают согласования — не показываем (Блок 6.3).
- Открытие `LineDetailsDrawer` по такой строке добавляет `lineId` в множество → индикатор
  исчезает (Блок 6.4), сохраняется в localStorage.

### B6. Сиды для демонстрируемости всех состояний

Чтобы клиент увидел все 11 статусов + подсветки + панель без ручных действий, засеять на
существующих согласованных кампаниях (напр. PR-2026-001/003) по одной строке каждого вида:
- одна строка с `pending.action==="change"` (Изменение на согласовании, светло-оранжевая,
  панель Поле/Было/Стало);
- одна с `pending.action==="addition"` (новая позиция после согласования);
- одна с `removalPending` (Исключение на согласовании) — уже есть сид на UN-2026-015;
- одна с `pending.rejected` (Отклонённые изменения + красный индикатор для КМ);
- одна `removed` (Отменена / Удалена) — уже есть;
- «Черновик» / «На согл. у ст. КМ» / «На согл. у КД» / «Переотправлено…» / «Согласовано и
  отправлено» покрываются существующими `campaign.status` сидами (18 кампаний уже дают эти
  состояния — проверено грепом).

Сиды детерминированы, per-browser localStorage только для «просмотренных отклонений».

## План проверки

- `build:promo` + `build:dashboard` зелёные.
- In-browser QA (Администратор / КД / КМ, 1440 + 390px):
  - фильтр «Все статусы»: каждое из 11 значений + «Все статусы» + «На согласовании (общее)»
    (последнее показывает все ожидающие);
  - светло-оранжевая подсветка **только** у повторных действий; первичное/согласованные —
    без подсветки; «Черновик» — компактная пометка; отменённые — серый+зачёркнуто;
  - иконка-глаз → панель «Детали изменений» (Поле/Было/Стало для изменения; «Запрос на
    исключение» + причина; отклонение — кто/дата/причина);
  - основная таблица показывает **согласованные** значения по строке с `pending` (не новые);
  - красный индикатор у КМ только после отрицательного решения, гаснет после открытия панели,
    переживает reload; у других ролей индикатора нет;
  - «Скрыть отменённые» скрывает только `removed`, не `removalPending` (Блок 5.6);
  - плашки/бейдж/янтарная обводка ячеек ушли (Блок 1.2/13);
  - подарки: «Подарок (1)/(2)» для фиксированных, «Подарок на выбор» подпись для choice,
    «+ Добавить подарок» работает.

## Ограничения мока

- Нет пер-персон identity → «Кто отправил/отклонил» = роль-метка (как в остальном моке).
- «Просмотренные отклонения» — per-browser localStorage.
- Согласование повторных изменений (вливание `pending` → актуальные) в этой волне —
  демо-переход/сид; полноценный workflow согласования правок — карточка согласования (Волна 3).
- Все 11 статусов достижимы через детерминированные сиды; часть — через переключение god-mode
  роли (для красного индикатора КМ).
- **Отклонённое исключение** (Блок 6.6: rejected exclusion → «Отклонённые изменения» +
  красный индикатор): текущий `rejectRemoval` просто восстанавливает строку
  (`removalPending=false`), отдельного persisted-состояния «исключение отклонено» нет.
  Красный индикатор + «Отклонённые изменения» демонстрируем на отклонённой **правке**
  (`pending.rejected`) — самом частом сценарии; отклонённое исключение оставляем возвратом
  строки в норму. Если клиент попросит — добавим `removalRejected` флаг отдельным пунктом.
