## 1. Контекст

Волны 1–3 «10-й части» закрыли краткий календарь (быстрые правки), полный календарь
(построчная модель статусов) и карточку согласования. Волна 4 — последний крупный
незакрытый блок по **плану акций**.

Экран уже прошёл три раунда доработок:

- «8-я часть» — пер-строчные решения проверяющего (`DecisionMap`, этапы КД/ОД);
- «6-я часть» — пер-строчный цикл отправки (`sendStatus`: `Черновик → Отправлено`);
- «7-я часть» §9 — журнал отклонений (`rejectionLog`) + панель деталей;
- «Группа A» T12 — персистентность всего перечисленного (`lib/plan-store.ts`).

Волна 4 достраивает то, что во всех трёх раундах осталось за скобками: **время**.

## 3. Диагноз по коду

1. Колонки «Коммерческий директор» / «Операционный директор» рендерятся исключительно из
   **сида** `getPlanApproval(id)` (`PlanApprovalTable.tsx`). Живые решения сессии (`decisions`)
   в них не попадают — видны только в бейдже «Статус строки». Это и есть R29.5: строка
   «Согласовано», а колонка этапа показывает «Ожидает согласования» без даты.
2. У строк без сид-записи (`PR-2026-008…016` и созданных вручную) колонки этапов — прочерки
   при любом состоянии.
3. **Дата отправки строки нигде не хранится**: `sendStatus` — это только `"draft" | "sent"`.
   Поэтому «дата повторной отправки» (R30.1) взять неоткуда, и SLA этапа не от чего считать.
4. `handleDelete` — жёсткое удаление, уже ограниченное черновиками. Согласованную строку
   удалить нельзя вовсе: R30.2 не реализован.
5. `AuditActionType` уже содержит «отправка на согласование» / «согласование» / «отклонение» /
   «изменение» / «отмена», `AuditObjectType` — «план», а `AuditLogTable` мержит
   `getLiveAuditEvents()`. Живые события плана попадут в `/audit` **без новых типов**.

## 4. Выбранный подход

**Пер-строчный журнал циклов**, дополняющий существующие слайсы (не заменяющий их).

Отвергнутые альтернативы:

- **Минимум** (живые даты + флаг «на удалении», без циклов) — «предыдущие даты и решения не
  затирать» (R30.1) становится нереализуемым: истории нет, только последнее решение.
- **Перестройка плана в независимые пер-строчные цепочки** (статус плана — производный) —
  концептуально чище, но это переписывание `PlanMode` и риск для поведения «6-й/7-й/8-й
  частей», которое клиент уже принял («повторное согласование запускается — это ок»).

## 5. Модель данных

Новый слайс в `lib/plan-store.ts` — `rowJournal: Record<rowId, PlanRowJournal>`:

```ts
/** Решение одного согласующего этапа в рамках цикла. */
interface PlanStageDecision {
  decision: "approved" | "rejected";
  at: string;        // ISO
  by: string;        // ФИО вошедшего пользователя (fallback — роль)
  role: string;      // роль согласующего
  comment?: string;  // единое поле «Комментарий» (§9.2 «7-й части») — для отклонения
}

/** Один цикл согласования строки: отправка → решения КД → ОД. */
interface PlanApprovalCycle {
  no: number;                              // 1-based
  sentAt: string;                          // ISO — дата (повторной) отправки
  sentBy: string;
  kd?: PlanStageDecision;
  od?: PlanStageDecision;
  closedAt?: string;                       // цикл закрыт без результата
  closedReason?: "return" | "edit";        // «Вернуть на доработку» / правка отправленной строки
}

/** Запрос на удаление ранее согласованной строки (R30.2). */
interface PlanRemovalRequest {
  requestedAt: string;
  requestedBy: string;
  reason: string;
  requiredStages: ("kd" | "od")[];         // снимок согласовавших этапов на момент запроса
  kd?: PlanStageDecision;
  od?: PlanStageDecision;
}

interface PlanRowJournal {
  cycles: PlanApprovalCycle[];             // от старых к новым
  removal?: PlanRemovalRequest;            // активный запрос
  removalHistory?: PlanRemovalRequest[];   // отклонённые запросы (не затираем)
}
```

**Отношение к существующим слайсам:**

- `sendStatus` / `decisions` — остаются как есть (их читают экспорт и текущая логика выбора).
  Журнал их **дополняет** датами и историей, а не заменяет.
- `rejectionLog` — переводится в режим **legacy read-only**: новые отклонения пишутся в журнал,
  старые персистентные записи по-прежнему читаются для отображения. Двойной записи нет
  осознанно — это ровно тот шов, на котором в E-4 разъехались `.role` / `.roles`.
- Хидрация: слайс отсутствует → `{}` → поведение байт-в-байт как сегодня.
- Сериализация: даты как ISO-строки (идиома стора), ревайв на чтение не нужен —
  деривации принимают ISO и конвертируют сами.

## 6. Новый модуль `lib/plan-approval.ts`

Чистый слой без React. Обоснование границы: `PlanMode.tsx` уже 1012 строк, а те же деривации
нужны таблице (`PlanApprovalTable`), панели истории и экспорту (`buildPlanCsv`) — три
потребителя одной логики.

### 6.1 Деривация ячейки этапа

Единственная функция на ячейку; сид — **fallback внутри неё**, чтобы таблица, панель и выгрузка
не могли разъехаться (урок E-3: вкладки согласуются только по конструкции).

```ts
interface StageCellData {
  reviewedAt?: Date;              // «Озн.» — только из сида
  sentAt?: Date;                  // «Отпр.» — из текущего цикла, иначе из сида
  decidedAt?: Date;
  decision?: "approved" | "rejected";
  status: PlanStageStatus;        // "onTime" | "overdue" | "waiting"
  overdueDays?: number;
  unit: "cal" | "work";           // единица просрочки
  by?: string;
  cycleNo?: number;               // проставляется при no > 1
}

marketingStageCell(row, journal, seed): StageCellData | undefined
directorStageCell(stage, row, journal, seed, ref?): StageCellData | undefined
```

### 6.2 Правила своевременности

| Этап | Старт этапа | Дедлайн | Единица |
|---|---|---|---|
| Директор маркетинга (Отпр.) | — | `startDate − PLAN_MARKETING_SUBMIT_LEAD_DAYS` (60 кал. дн.) | календарные |
| Коммерческий директор | `cycle.sentAt` | `addWorkingDays(старт, PLAN_DIRECTOR_SLA_WORKING_DAYS)` (3 раб. дн.) | рабочие |
| Операционный директор | `cycle.kd.at` (только при `approved`) | `addWorkingDays(старт, 3)` | рабочие |

Исходы:

- решение есть и `at ≤ дедлайн` → **«В срок»**;
- решение есть и `at > дедлайн` → **«Просрочка +N»** (`N` = `workingDaysBetween(дедлайн, at)`
  для директоров, `getOverdueDays(дедлайн, at)` для маркетинга);
- решения нет, этап начат, `now ≤ дедлайн` → **«Ожидает согласования»**;
- решения нет, этап начат, `now > дедлайн` → **«Ожидает согласования · просрочка +N раб. дн.»**
  (утверждено пользователем; раздел про контроль сроков, молчащая просрочка — пробел). Не
  блокирует ничего;
- этап не начат (у ОД нет согласования КД) → **«Ожидает согласования»** без просрочки.

Бейдж `StageStatusBadge` получает проп `unit` и печатает «кал. дн.» / «раб. дн.» — по
конвенции проекта дедлайны всегда календарные, SLA согласования — рабочие; сейчас везде
безликое «+N дн.».

### 6.3 Сид-строки и материализация цикла

Строки с записью в `PLAN_APPROVALS`, но без журнала, читаются из сида — поведение сегодняшнее.
При первом живом событии по такой строке цикл №1 **материализуется** из сида:
`sentAt = seed.marketing.sentAt`, если запись есть, иначе `now`. Так SLA КД считается от
реальной отправки, а не от момента клика.

Чистый хелпер `ensureCycle(journal, seedSentAt, actor)` используют все писатели; читатели
вызывают `currentCycle(journal)` с сид-fallback'ом внутри деривации ячейки.

### 6.4 Статус строки и права

```ts
type PlanRowLifecycle =
  | "draft" | "sent" | "approved" | "rejected" | "removal-pending";

planRowLifecycle(rowId, journal, sendStatus, decisions, planStatus): PlanRowLifecycle
canDecideRemoval(role, journal): "kd" | "od" | undefined
requiredRemovalStages(journal): ("kd" | "od")[]
```

Журнал авторитетен, когда он есть; иначе — сегодняшняя логика (`isApproved && sent` и т. д.),
чтобы сид-строки и снапшоты прошлых сессий не изменили вид.

## 7. Поведение по требованиям

### 7.1 R29.5 — дата решения и своевременность по этапам

Колонки КД/ОД показывают живое решение: дата-время + «В срок» / «Просрочка +N раб. дн.».
Побочный эффект — чинятся строки без сид-записи (`26-8…16` и созданные вручную): сейчас там
прочерки при любом состоянии, после отправки колонки начинают заполняться.

### 7.2 R30.1 — циклы согласования

Повторная отправка (после правки строки или после «Вернуть на доработку») **добавляет новый
цикл**, а не перетирает предыдущий:

- таблица показывает **текущий** цикл; при `no > 1` в колонке «Директор маркетинга» рядом с
  «Отпр.» выводится метка «Цикл N» (одно место, чтобы не дублировать её в трёх колонках);
- «Отпр.» в колонке маркетинга = `sentAt` текущего цикла (дата повторной отправки);
- предыдущие циклы — в панели истории и в аудит-логе;
- закрытие цикла: `closedReason: "return"` при «Вернуть на доработку», `"edit"` при правке
  отправленной строки (существующий переход «строка → Черновик»).

Плановая цепочка (`planStatus`) при этом ведёт себя как сегодня: `sendSelected` заново
открывает «На согл. с КД», когда план в терминальном состоянии или на стадии владельца.
Клиент этот поток принял — меняем только отображение и историю.

### 7.3 R30.2 — удаление через согласование

Правила:

Решение принимается по **последнему циклу** строки:

- строка, у которой в последнем цикле **нет ни одного согласования** (черновик; отправлена, но
  решений нет; либо цикл закрыт правкой / возвратом на доработку) — удаляется сразу, как
  сегодня. Это буквальное прочтение «Если строка ранее была согласована…»: правка уже вывела
  строку из согласованного плана — повторно спрашивать не за что;
- строка, у которой в последнем цикле **есть ≥1 согласование**, — «Удалить» открывает
  `ReasonDialog` («Запросить удаление строки», обязательная причина) → создаётся `removal` с
  `requiredStages` = снимок согласовавших этапов этого цикла;
- строка **остаётся в плане** со статусом **«Удаление на согласовании»**; чекбокс выбора,
  «Изменить» и «Удалить» для неё скрыты, пока запрос активен;
- решение принимает КД или ОД (тот, кто в `requiredStages` и ещё не решил) **из боковой
  панели строки**, **независимо от `planStatus`**. Обоснование: при «Утверждён»
  `actorForPlanStatus` возвращает `undefined` — очередь, выведенная из агрегатного статуса, не
  увидит новый класс работы (урок Волны 3). Третий режим массового выбора не вводим: их уже
  два (отправка / согласование);
- все требуемые этапы согласовали → строка уходит в `deletedIds` (существующий tombstone-набор);
  журнал по её id сохраняется, событие пишется в аудит;
- любое отклонение → активный `removal` переносится в `removalHistory`, строка живёт дальше в
  прежнем состоянии, причина отклонения видна в панели;
- строки с активным `removal` **исключаются из знаменателя** проверки «advance when all
  approved» в `approveSelected` — иначе план перестанет продвигаться.

## 8. UI

### 8.1 `PlanApprovalTable`

- ячейки `MarketingCell` / `DirectorCell` рендерятся из `StageCellData`, а не напрямую из сида;
- `StageStatusBadge` печатает единицу («кал. дн.» / «раб. дн.») и умеет «Ожидает согласования ·
  просрочка +N»;
- `RowLifecycleBadge` += **«Удаление на согласовании»** (оранжевая плашка, кликабельна → панель);
- новое строковое действие **«История»** (иконка), доступное всем ролям — панель истории строки
  теперь достижима не только через «Отклонено»;
- `rowCheckable` не отдаёт чекбокс строкам с активным `removal`.

### 8.2 `PlanRejectionDrawer` → `PlanRowHistoryDrawer`

Переименование + расширение (один потребитель — `PlanMode`, риск локальный). Секции:

1. **Заголовок** — «26-N» + название строки.
2. **Запрос на удаление** (когда есть) — кто, когда, причина, список требуемых этапов со
   статусом каждого + кнопки «Согласовать удаление» / «Отклонить удаление» для действующей роли.
3. **Текущий цикл** — «Цикл N · отправлено DD.MM.YYYY HH:MM», решения КД/ОД с датой и сроком.
4. **История согласования** — прежние циклы (новые сверху), возвраты и правки, отклонённые
   запросы на удаление.

**Обратная совместимость:** если журнала по строке нет, панель рендерит сегодняшний вид из
legacy `rejectionLog` — без слияния и дедупликации.

## 9. Экспорт и аудит

**`buildPlanCsv`:** колонки этапов и отклонения читаются из журнала (сид — fallback), плюс
новая колонка «Цикл согласования». Состав столбцов «7-й части» §9.5 сохраняется.

**Аудит** — живые события через `appendAuditEvent`, **без новых типов** (`AUDIT_ACTION_META` —
`Record<AuditActionType, …>`, его неисчерпаемость невидима для транспайл-онли билда и уже
ломала аудит в E-4):

| Событие | `action` | `objectType` | Комментарий |
|---|---|---|---|
| Отправка строки на согласование | «отправка на согласование» | «план» | «Цикл N» |
| Согласование КД / ОД | «согласование» | «план» | статус до → после |
| Отклонение | «отклонение» | «план» | комментарий отклонения |
| Возврат на доработку | «изменение» | «план» | «Возврат на доработку» |
| Запрос на удаление строки | «изменение» | «план» | «Запрос на удаление: <причина>» |
| Согласование удаления одним этапом | «согласование» | «план» | «Удаление согласовано (КД/ОД)» |
| Отклонение удаления | «отклонение» | «план» | причина |
| Удаление применено (согласовали все требуемые этапы) | «отмена» | «план» | «Строка удалена из плана» |

Последнее согласование удаления порождает **две** записи — решение этапа и факт удаления: это
два разных факта, и в аудите они читаются как «кто решил» и «что произошло с планом».

`objectLabel` = название строки, `campaignId` = id строки. Вкладка «Аудит-лог» уже мержит
`getLiveAuditEvents()` — подхватит сама.

## 12. Риски

1. **Расхождение сид / лайв** — главный источник дефектов. Митигация: единственная деривация
   `stageCell()` на всех потребителях; сид только внутри неё; в ревью явная проверка, что
   таблица, панель и CSV дают одинаковые значения для одной строки.
2. **`planStatus` vs пер-строчные решения по удалению** — решение намеренно вне плановой
   цепочки. Проверить, что строки с pending-удалением не блокируют «advance when all approved».
3. **Транспайл-онли билд** (`vite build` = esbuild, без `tsc`) не ловит несоответствия типов,
   неисчерпаемые `Record` и импорты несуществующих экспортов. Каждое ревью задачи обязано
   содержать явные типовые проверки чтением.
4. **Радиксовые ловушки экрана** (обе уже кусали именно `PlanMode`): контролируемый `Dialog`,
   открываемый обычной кнопкой, только через `setTimeout(…, 0)`; `DropdownMenu`/`Popover` под
   shared `<Button asChild>` рендерятся за экраном — использовать нативный `<button>` +
   `buttonVariants`. Новый `ReasonDialog` удаления открывается из строки таблицы — случай
   ровно этот.
5. **Tombstone-пул номеров** — `nextPlanPromoNo` уже учитывает `deletedIds`; удаление через
   согласование добавляет id туда же, поведение сохраняется.

## 13. Критерии приёмки

- [ ] **R29.5** — после живого решения КД/ОД колонка этапа показывает дату-время и «В срок» /
      «Просрочка +N раб. дн.»; то же для строк без сид-записи.
- [ ] **R29.5** — строка, ожидающая решения дольше 3 раб. дн., показывает «Ожидает согласования
      · просрочка +N раб. дн.» и ничего не блокирует.
- [ ] **R30.1** — правка согласованной строки → «Черновик» → повторная отправка создаёт цикл 2;
      таблица показывает даты цикла 2, панель — цикл 1 в истории; переживает перезагрузку.
- [ ] **R30.2** — «Удалить» на согласованной строке не удаляет её, а создаёт запрос; строка
      остаётся со статусом «Удаление на согласовании»; КД (и ОД, если он согласовывал) решают
      из панели; после всех согласований строка исчезает, в `/audit` есть записи запроса и
      решения; отклонение возвращает строку в план с видимой причиной.
- [ ] Черновик и отправленная-без-решений строка удаляются сразу, как раньше.
- [ ] CSV плана содержит колонку «Цикл согласования» и даты/статусы этапов из журнала.
- [ ] Оба билда зелёные (`build:promo`, `build:dashboard`); in-browser QA на 1440 и 390 px в
      ролях Директор маркетинга / КД / ОД; светлая и тёмная темы.
- [ ] Пустой `localStorage` → экран выглядит и ведёт себя как до изменений (сид-строки).
