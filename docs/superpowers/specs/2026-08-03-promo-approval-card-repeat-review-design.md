## 1. Проблема

Волна 2 построила построчную модель статусов полного календаря: правка согласованной позиции,
добавление новой позиции после согласования и запрос на исключение уходят в `PromoLine.pending`
(соотв. `removalPending`), таблица продолжает показывать **согласованные** данные, а новые видны
только в read-only панели «Детали изменений».

Контур не замкнут: **решения по этим повторным действиям принимать негде**. Карточка согласования
(`/approvals/:id`) осталась в модели «первичного согласования»:

- показывает только строки текущего КМ (`lines.filter(l => l.kmId === item.kmId)`) — нет контекста акции;
- все строки одинаково выбираемы — ранее согласованные попадают в повторное решение;
- ничего не знает про `pending` / `removalPending` — нет ни подсветки, ни «Было/Стало», ни причины;
- `buildReviewItems` порождает заявки только по `kmStatuses`, ожидающим проверяющего, поэтому
  у согласованной PR-2026-003 (где как раз лежат демо-seeds Волны 2) **заявки вообще нет**.

## 2. Требования клиента (16 пунктов, дословно → решение)

| № | Требование | Решение |
|---|---|---|
| 1 | «Отправлено на согласование» → **«Получено на согласование»** (момент получения задачи текущим проверяющим на текущем этапе) | InfoRow переименован, значение = `stageSlaStart(item)` (уже учитывает этап КД / авто-передачу) |
| 2 | Для автопереданных — **«Авто-передано КД» + дата** в карточке; общий список не менять | Отдельный InfoRow с `seniorOverdueInfo(item).autoForwardedAt`; `ReviewQueueTable` не трогаем |
| 3 | При повторной отправке «Получено на согласование» = дата **текущей повторной** отправки | `receivedAt(item, lines)` = max(`stageSlaStart`, последняя дата повторного действия по строкам, требующим решения) |
| 4 | Показывать **весь список номенклатур по промо**, включая ранее согласованные | Карточка читает `getPromoLines(campaignId)` целиком (не только строки своего КМ) |

| 6 | Строки с повторным действием КМ (изменение / добавление / удаление ранее согласованной) — **светло-оранжевые** | `isRepeatActionPending(line)` из Волны 2 (единый источник с полным календарём) |
| 7 | Клик по оранжевой строке → **боковая панель**: тип изменения, «Было/Стало», комментарий КМ, дата повторной отправки, срок/SLA если прошёл | Новый `LineChangeDrawer` |
| 8 | Добавление номенклатуры → тоже оранжевая; в панели тип «**Добавлена номенклатура**» + данные добавленной строки | `pending.action === "addition"` → блок с полями добавленной позиции |
| 9 | Удаление ранее согласованной → тоже оранжевая; тип «**Удаление номенклатуры**», в «Было/Стало» — была согласована → предлагается удалить | `removalPending` → синтетическая строка сравнения «Согласована в акции» → «Предложена к удалению» |
| 10 | Если по строке **срок прошёл** — обязательно показать в панели | Блок SLA: «просрочка +N раб. дн.» / «осталось N раб. дн. (до DD.MM.YYYY)» из `itemSla` |
| 11 | Переключатель **«Все строки / Только изменения»** | ToggleGroup над таблицей (`flex-none whitespace-nowrap` — урок S2 Phase 1) |
| 12 | Счётчик «**На согласовании: N строк · Согласовано ранее: M строк**» | `approvalCounters(rows)` |
| 13 | **Колонку статуса не выводить** | Признак повторного действия = подсветка + панель |
| 14 | Согласование/отклонение **только по строкам, требующим решения** | Выбор и массовые действия ограничены `requiresDecision` |

## 3. Дизайн

### 3.1 Слой данных — повторные заявки

`ReviewKind` получает третье значение **`"repeat"`**. `buildReviewItems` дополнительно порождает
заявку на (акцию × КМ), если акция **согласована** и у этого КМ есть строки с неразрешённым
повторным действием: `line.pending && !line.pending.rejected` **или** `line.removalPending && !line.removed`.

- `submittedAt` = самая поздняя дата повторного действия среди этих строк (⇒ §3 выполняется
  существующим `stageSlaStart`, без новой временной сущности);
- `kmStatus` = «На согласовании у старшего КМ» ⇒ работает вся существующая машинерия:
  `effectiveReviewer`, живая авто-эскалация к КД, `itemSla`, `displayKmStatus`;
- ключ `reviewItemId(campaignId, kmId)` — совпадений с data-заявками нет по построению
  (терминальный статус vs ожидающий), плюс явный guard.

Заявки видны в очереди `/approvals` (иначе до карточки не дойти) — **отображение самой очереди не меняется** (§2).

### 3.2 Слой карточки — `lib/approval-card.ts` (чистый)

```
ApprovalRowKind = "change" | "addition" | "removal" | "approved-earlier" | "primary" | "rejected-repeat" | "other-pending"
ApprovalRow  { line, kind, requiresDecision, isRepeat, sentAt?, comment?, requestType?, fields? }
buildApprovalRows(campaign, lines, item)   // строки всей акции + классификация
approvalCounters(rows) → { pending, approvedEarlier }
```

Классификация строки:
1. `removed` / `pending.rejected` / чужой КМ → read-only, метка по реальному статусу;
2. повторное действие **этого** КМ → `requiresDecision = true`, оранжевая;
3. акция согласована, повторного действия нет → «Согласовано ранее» + замок;
4. акция на первичном согласовании → `primary`, решение требуется (текущее поведение S3 — без регресса).

> Важно: «Согласовано ранее» ставится только там, где строка **действительно** согласована.
> Чужая незакрытая позиция помечается своим реальным статусом (`lineDisplayStatus`), а не ложным «Согласовано ранее».

### 3.3 Решения — `lib/line-decision-store.ts` (localStorage `promo:line-decisions`)

Прецедент — `plan-store.ts` (Группа A T12): решения переживают перезагрузку и видны с обоих экранов.

```
LineDecision { lineId, campaignId, action, kind: "approved"|"rejected", by, at, reason? }
getLineDecisions() / recordLineDecision() / recordLineDecisions() / clearLineDecisions()
applyLineDecisions(lines) → PromoLine[]   // согласовано: pending применён и снят; отклонено: pending.rejected
```

Применение согласованного изменения точное: `LinePendingChange.fields[]` получает **опциональное
`value`** (сырое новое значение). `mergePendingChange` пишет его из патча; для старых сидов —
резервный числовой разбор форматированной строки (идиома `EditableCell`).

### 3.4 UI

- `SubmittedLinesPanel` — переработка: строки всей акции, замок + «Согласовано ранее», оранжевые
  строки повторных действий, клик по строке, **без колонки статуса**, тумблер + счётчик, мобильные карточки.
- `LineChangeDrawer` — новая боковая панель проверяющего (структура «Поле/Было/Стало» переиспользует
  контракт `LineDetailsDrawer` Волны 2) + блок SLA + два действия. Панель полного календаря остаётся
  read-only: она для КМ, эта — для проверяющего.
- `ReviewActionsPanel` — массовые действия сужены до строк с решением.

## 4. Границы

- Волны 4–6 не входят.
- Очередь `/approvals` не переоформляется (§2).
- Идентичности по людям в моке нет: «кто отправил / отклонил» — ярлык роли (ограничение Волны 2).
- Решения хранятся в localStorage браузера, как и `plan-store` / read-set уведомлений.
