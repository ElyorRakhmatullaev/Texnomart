# Broker · Третья итерация ветки Alif — ТЗ на основе API (8 экранов)

> Дата: 2026-08-21 · Скоуп: `Broker/**` + документация. Promo и Dashboard не затрагиваются.
> Источник: **`alif_ui_tz.md`** («ТЗ для UI/UX дизайнера — Флоу оформления рассрочки Alif», получено 2026-08-19), внешний к репозиторию, как и оба предшественника. Написан **по API-документации Alif**: эндпоинты, поля payload, коды статусов.
> Предшественники: `2026-08-18-broker-alif-checkout-popup-design.md` (текущая архитектура — вся ветка в попапе) и `2026-08-18-broker-alif-rework-tz-design.md` (содержимое шагов). Оба остаются в силе там, где новое ТЗ их не переписывает.
> Дельта, зафиксированная в `Broker/CLAUDE.md` § Pending, — предварительная; эта спека её уточняет и заменяет.

## 1. Что закрывает эта итерация

Сверка ТЗ с кодом дала **~30 открытых пунктов**. Целиком готовы 2 экрана из 8 (6 «OTP кредита» и 8 «Договор»), почти готовы 2 (5 «Холд», 7 «Оформление»), частично 3 (1 «Предложение», 2 «Привязка карты», 3 «Доп. данные»), отсутствует 1 (4 «Создание заявки»). Не сделана вся сквозная часть: модель статусов заявки, отмена заявки, продажа Alif, единый вывод ошибок API, «сессия истекла», тийины.

Несущий пробел — **модель статусов заявки**. От неё зависят результат экрана 4, правило отмены холда, отмена заявки и продажа. Поэтому она идёт первой волной, до экранов.

## 2. Ключевые решения

### 2.1. Всё остаётся в попапе; фаз становится семь

Маршрутов по-прежнему 4, ветка Alif — фазы одного `AlifCheckoutDialog`. Фаза по-прежнему **не хранится**, а деривируется из состояния. Порядок проверок читается сверху вниз как «что сейчас блокирует прогресс»:

```
if (creditConfirmed)                                   → "success"     // экраны 7 (итог) + 8
if (!offerConfirmed)                                   → "offer"       // экран 1
if (!alifCard)                                         → "card"        // экран 2
if (!relations)                                        → "details"     // экран 3
if (!application)                                      → "application" // экран 4
if (prepayment > 0 && holdStatus !== "confirmed")      → "hold"        // экран 5
                                                       → "otp"         // экраны 6–7
```

**Холд переезжает с позиции «до доп. данных» на «после создания заявки»** — по ТЗ (экран 5) заявка сначала создаётся со статусом `NEW`, и только потом удерживается предоплата. Урок 18.08 при этом сохраняется: холд остаётся **выше** `otp`, поэтому отмена холда с шага OTP по-прежнему возвращает оператора на холд, а не оставляет его на экране, деньги под которым уже разблокированы. Обратный порядок (`otp` выше `hold`) воспроизвёл бы тот баг — не менять.

`relations` и `survey` сохраняются одним действием экрана 3, поэтому проверки на `survey` в деривации нет — заполненные `relations` означают, что экран пройден целиком.

Существующая задержка `HOLD_TO_DETAILS_DELAY_MS = 600` мс сохраняется, но её единственная цель теперь `hold → otp`: в новом порядке это единственный выход с фазы холда. Константа переименовывается в `HOLD_EXIT_DELAY_MS`, чтобы имя не врало.

### 2.2. Выбор условия — только на экране 1

Сейчас срок выбирается чипами на карточке банка **до** попапа, а фаза `confirm` — сводка в одну строку. ТЗ делает выбор условия экраном 1 внутри ветки. Держать выбор в двух местах — ровно та конструкция, что 18.08 породила баг «договор на 6 мес. вместо выбранных 12» (локальный `useState` карточки перезаписывал подтверждённый срок при повторном открытии).

Поэтому: **чипы срока и строка «Срок 0-0-N» уходят с `BankCard`**. Карточка показывает логотип, статус, «Доступный лимит», «Предоплата» и «Оформить». `selectAlif(tenor)` заменяется на `selectPlan(planId)`, вызываемый из `OfferPhase`, и гейт-заморозка `if (!offerConfirmed)` в `BanksPage` становится не нужна — уходит вместе с ней целый класс багов.

Это видимое отличие от Figma-фреймов 27/32/46. Отмечено сознательно: ТЗ новее и явно переносит выбор условия внутрь ветки. Если PM захочет вернуть чипы — они станут превью, предвыбирающим план на экране 1, но источником правды всё равно останется экран 1.

### 2.3. Отмена холда — только пока заявка `NEW`

Конфликт между ТЗ и чек-листом PM от 19.08, который надо разрешить явно.

19.08 было сделано: «отмена холда доступна с любой поздней фазы» (плашка `HoldStatusBar` на `details`/`otp`). ТЗ (экран 5): отмена холда допускается **только пока заявка в статусе «Новый»**, а после холда заявка уходит на рассмотрение.

Решение — следовать ТЗ, потому что оно написано по API и описывает реальное поведение бэкенда. Возможность выйти из уже удержанного холда при этом не теряется, а переезжает под **«Отменить заявку»** (доступна в `NEW`/`APPROVED`), которая снимает холд вместе с заявкой. Мёртвой зоны не образуется: `REVIEWING` в моке длится ~2,5 с и сменяется на `APPROVED`.

`HoldStatusBar` соответственно меняет поведение: пока `NEW` — показывает «Отменить холд»; после — остаётся информационной плашкой без действия, потому что выход из этого состояния даёт «Отменить заявку» в шапке попапа (§5). Двух кнопок отмены на одном экране быть не должно. Видимое состояние «Холд отменён» остаётся достижимым (в `NEW`).

### 2.4. Демо-триггеры — одной панелью

Урок 19.08: ветка обработки ошибки, которую нечем вызвать, — мёртвый код. Новых недостижимых исходов много: отказ скоринга (экран 1), `phone_match: false` (экран 2), три результата и шесть бизнес-ошибок (экран 4), истечение сессии (сквозное).

Вместо россыпи чипов по фазам — **одна панель `checkout/DemoScenarioBar.tsx`**, которую рендерит сам `AlifCheckoutDialog` тонкой полосой внизу попапа. Она знает текущую фазу и показывает релевантные ей переключатели плюс всегда доступный «Сессия истекла». Одно место, один визуальный язык, одна точка удаления при интеграции с API — помечена и в коде, и в `Broker/CLAUDE.md`.

Чипы MyID (`MYID_DEMO_SCENARIOS`) остаются на месте: они завязаны на фазы съёмки и живут вне попапа. Унификация с ними — не в этом скоупе.

### 2.5. Прогресс: внешний степпер + внутренний «Шаг N из 7»

ТЗ просит «шаг 1 из N» и формат мастера. Внешний `ScoringStepper` описывает весь скоринг (5 шагов) и остаётся как есть; внутри попапа добавляется тонкая строка «Шаг N из 7 · <название>» + `Progress`. `PHASE_INDEX` расширяется: `offer`/`card` → 2, `details`/`application`/`hold` → 3, `otp`/`success` → 4.

### 2.6. Ключ хранилища — `v2`

`ScoringFlowState` меняется несовместимо (`tenor` → `planId`, `additionalData` → `relations` + `survey`, добавляется `application`). Чтение делает `{...INITIAL, ...parsed}`, так что старый снимок в `sessionStorage` дал бы полусостояние. `STORAGE_KEY` меняется на `broker:scoring-flow:v2`.

## 3. Новый чистый модуль — `lib/alif-application.ts`

Вся неUI-логика заявки в одном месте, без React, тестируемая чтением:

| Группа | Экспорт |
|---|---|
| Статусы | `ApplicationStatus` (7 значений), `APPLICATION_STATUS_META` (подпись + цвет по таблице §5 ТЗ) |
| Правила | `canCancelApplication` (`NEW`/`APPROVED`), `canCancelHold` (`NEW`), `canSell` (`ACTIVE`), `canUnsell` (`SOLD`) |
| Деньги | `monthlyPayment(principal, months)`, `commissionFor(principal, months)`, `tiyinToSum`, `sumToTiyin`. `principal` — сумма заказа за вычетом предоплаты; комиссия — процент по сроку из сид-таблицы `COMMISSION_RATES`, платёж = (principal + комиссия) / срок, округление до тысяч сум |
| Планы | `AlifPlan { id, duration, amount, monthlyPayment, commission, promo? }`, `buildPlans(limit, durations)` |
| Ошибки | `ApplicationErrorKey` + `APPLICATION_ERRORS` — шесть текстов §«Бизнес-ошибки» ТЗ дословно |
| Отмена | `CANCEL_REASONS` — девять пунктов §4 ТЗ дословно, с ключами |

Суммы в моке хранятся **в сумах**. `tiyinToSum`/`sumToTiyin` существуют для полей, которые в API ходят в тийинах (сумма холда), и помечают эти места комментарием — чтобы при интеграции конвертация оказалась там, где нужна, а не искалась заново.

## 4. Экран за экраном

### Экран 1 — `checkout/OfferPhase.tsx` (заменяет `ConfirmPhase.tsx`)

Список планов **3/6/12/18/24 мес.**, по каждому: сумма лимита, ежемесячный платёж, комиссия, метка промо (сид — на одном плане). Выбор одного, «Продолжить» → `selectPlan(id)` + `confirmOffer()`. Состояния: «Рассчитываем лимиты…» (существующая задержка ~6 с, `limits_calculating_in_progress`), «планы» (`limits_calculated`), **«Отказ»** — `reject_reasons` понятным текстом + «Назад к банкам» (закрывает попап). `BANKS.alif.tenors` приводится к набору ТЗ. Демо-переключатель: «Одобрено / Отказ».

### Экран 2 — `checkout/CardAttachPhase.tsx` (новый)

Привязка карты **к Alif** внутри ветки — отдельно от общей привязки на «Верификации», которая остаётся: там карта заводится до выбора банка, здесь она привязывается к конкретному банку (`request-attach`). Переиспользует `OtpPanel variant="card"`. Показывает маску телефона, куда ушёл код (`********2440`), после успеха — маску карты в формате Alif (`860012******3456`, новый хелпер `maskPanAlif`, существующий `maskCardNumber` остаётся для холда). Предупреждение при `phone_match: false`. Лимит попыток и срок жизни кода уже есть в `OtpPanel`; текст исчерпания приводится к формулировке ТЗ. Демо-переключатель: «Телефон совпадает / не совпадает».

### Экран 3 — `checkout/DetailsPhase.tsx` (переработка)

Два фиксированных доверительных лица заменяются **списком родственников**: тип родства, телефон, **имя**; «Добавить родственника», удаление, минимум один. Валидации: номера не совпадают между собой и не совпадают с номером клиента (`BROKER_CLIENT.phone`). Анкета: сфера деятельности (`activity_area_id`, сид-список), предпочитаемый язык (ru/uz), «есть автомобиль» (опционально). **«Дата списания оплаты» уезжает отсюда на экран 4** как `first_payment_date` — в ТЗ на этом экране её нет.

Существующая машинка маски телефона (`extractDigits` + `clampPhoneCursor`, защита курсора от порчи префикса `+998`) переносится без изменений и переиспользуется каждой строкой списка.

### Экран 4 — `checkout/ApplicationPhase.tsx` (новый)

Карточка товара из сида «1С»: название, категория, цена, IKPU, SKU. Поле IMEI/маркировки. **Дата первого платежа** — не дальше +45 дней, по умолчанию +30. Итог: сумма, комиссия, срок, ежемесячный платёж. «Создать заявку» → `createApplication()`.

Результат бейджем: `APPROVED` (сразу), `REVIEWING` (~2,5 с «на рассмотрении» → `APPROVED`), `REJECTED`. Шесть бизнес-ошибок показываются на месте формы с иконкой ошибки; ошибка суммы/IKPU дополнительно подсвечивает конкретное поле (§6 ТЗ). Демо-переключатель — один `Select` с девятью исходами (3 статуса + 6 ошибок).

Если по предложению есть предоплата (`ALIF_PREPAYMENT > 0` — в текущем сиде всегда), заявка создаётся со статусом `NEW` (`store-new`) и следующая фаза — холд; иначе сразу `REVIEWING`/`APPROVED` и следующая фаза — OTP. Предоплата в моке задана на уровне банка, а не плана, — так же, как её читает деривация фаз в §2.1.

Переход `REVIEWING → APPROVED` мокается задержкой `APPLICATION_REVIEW_DELAY_MS = 2500` — тем же приёмом, что проверка MyID.

### Экран 5 — `checkout/HoldPhase.tsx` (доводка)

Добавляются `hold_at` / `hold_till` (даты удержания, сид: сейчас и +7 дней) и `card_pan`. Правило §2.3: «Отменить холд» — только пока `NEW`. Четыре статуса и «Удержать заново» сохраняются.

### Экраны 6–7 — `checkout/CreditOtpPhase.tsx`, `checkout/SuccessPhase.tsx` (доводка)

В сводку добавляется **ежемесячный платёж**. При оформлении фиксируются `contractNo` и **`contractDate`** — сейчас дата считается `new Date()` на рендере, поэтому при повторном открытии показывает сегодняшнее число вместо даты подписания; это дефект, а не только пробел ТЗ. Статус заявки переходит в `ACTIVE`.

### Экран 8 — без изменений

Скачивание и просмотр `contract-mock.pdf`, реквизиты договора, постоянный вход через «Открыть договор» на карточке Alif — всё уже есть.

## 5. Сквозные элементы

| Элемент | Решение |
|---|---|
| Бейдж статуса | `checkout/ApplicationStatusBadge.tsx` по `APPLICATION_STATUS_META`; место — шапка попапа рядом с прогрессом, плюс карточка Alif на `/scoring/banks` |
| Отмена заявки | `checkout/CancelApplicationDialog.tsx` — `AlertDialog` с выбором одной из девяти причин, обязателен выбор; доступна в `NEW`/`APPROVED` из шапки попапа. Снимает холд, переводит заявку в `CANCELLED` |
| Продажа Alif | Кнопки «Продать Alif» (`ACTIVE` → `SOLD`) и «Отменить продажу» (`SOLD` → `CANCELLED`) на фазе `success` |
| Ошибки API | `checkout/PhaseError.tsx` — единая плашка «иконка + `message`» плюс проп подсветки поля. Оба формата ошибок ТЗ сводятся в моке к одному `{ key, message }` |
| Сессия истекла | Флаг `sessionExpired` в состоянии; при нём попап показывает вместо контента фазы плашку «Сессия Alif истекла» + «Обновить сессию» (сбрасывает флаг, возвращает на ту же фазу). Триггер — демо-панель |
| Загрузка | Фазы `card`, `application`, `otp` получают состояние ожидания ответа (кнопка в спиннере, контент заблокирован) — §2 ТЗ требует три состояния на каждом экране |

## 6. Состояние потока

```ts
alifLimitStatus: "pending" | "ready" | "rejected"   // + отказ скоринга
offerConfirmed: boolean
planId?: string                                      // condition_id
alifCard?: { pan: string; phone: string; phoneMatch: boolean }
relations?: Relation[]                               // { type, phone, name }
survey?: { activityAreaId: string; language: "ru" | "uz"; car?: boolean }
application?: {
  id: string; status: ApplicationStatus; createdAt: string
  firstPaymentDate: string; imei?: string
  amount: number; commission: number; duration: number
  cancelReasonKey?: string
}
hold?: { at: string; till: string; cardPan: string }
contractDate?: string
sessionExpired?: boolean
```

Удаляются: `tenor` (→ `planId`), `additionalData` (→ `relations` + `survey`), `alifSelected` (→ `planId`). Сохраняются: `cards`, `photoDone`, `myidDone`, `holdStatus`, `checkoutOpen`, `creditConfirmed`, `contractNo`, `oneCOrderNo`.

## 8. Вне скоупа

Шаги 1–2 (верификация, фото/MyID) не меняются — кроме того, что общая привязка карты остаётся как есть. Реальная интеграция с API, поллинг статуса заявки, ветка Iman, «Подбор товара», тёмная тема, внутристраничный просмотрщик PDF, i18n (язык в анкете — поле данных, не переключатель интерфейса) — по-прежнему вне скоупа.

## 9. Риски

- **Фазовая машина растёт с 5 фаз до 7**, а порядок проверок в `checkoutPhaseOf` — несущая конструкция, которую уже один раз чинили. Каждая новая строка вставляется с обоснованием, откаты (отмена холда, отмена заявки, истечение сессии) проверяются кликами.
- **Типов нет**: в `Broker/` отсутствуют и `typescript`, и `tsconfig.json`, `vite build` транспилирует через esbuild без проверки. Зелёный билд ничего не доказывает — проверка только чтением и браузером.
- **§2.2 и §2.3 — видимые отклонения** от Figma и от поведения, согласованного 19.08. Оба отмечены здесь явно и легко откатываются, если PM решит иначе.
