## T1 — слой данных: повторные заявки (§1–§3 основание, §4 источник строк)

1. `ReviewKind` += `"repeat"`.

3. `PromoLine.removalRequestedAt?: string` + `LineSeed.removalRequestedAt` (дата запроса на исключение —
   нужна панели §7 и расчёту §3).
4. `lineNeedsRepeatDecision(line)` + `repeatActionAt(line)` — единый предикат для UI и построения заявок.
5. `buildReviewItems`: после основного цикла добавить повторные заявки по согласованным акциям,
   сгруппировав строки с неразрешённым повторным действием по `line.kmId` (не по `participatingKmIds` —
   L-0022/L-0023 принадлежат km-1, которого нет в списке участников PR-2026-003). Guard от коллизии ключей.
6. `receivedAt(item, lines)` — §1/§3.
7. Сид L-0024 (PR-2026-003, km-4): `removalPending` + причина + `removalRequestedAt` = 31.07.2026 10:30.

## T5 — шапка, решения, история (§1, §2, §3, §14, §16)

`ApprovalDetailPage.tsx`:
1. «Получено на согласование» = `receivedAt` (§1/§3); новый InfoRow «Авто-передано КД» + дата (§2).
2. Хост таблицы и панели; `selected` ограничен строками с решением (§14).
3. `handleLineDecision(lineId, "approve" | "reject", reason?)` → `recordLineDecision` + комментарий в
   `item.comments` (что именно отклонено и почему, §16) + тост.
4. Когда решения приняты по всем строкам заявки — `approve(item.id, actingAsRole)` продвигает её по
   существующей цепочке; отклонение возвращает набор КМ (существующий `reject`).
5. `ReviewActionsPanel.tsx`: копия и счётчики для `kind === "repeat"`, массовые действия по выбранным.

**Проверка:** согласование строки → значения актуальны в полном календаре, подсветка снята;
отклонение → «Отклонённые изменения» + красный индикатор у КМ + запись в истории.
